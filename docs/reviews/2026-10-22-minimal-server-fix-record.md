## 3. 启动、日志与入服协议

### M01：允许忽略通信版本字符串限制

**现象与需求。** 最初要求“启动服务器忽略通信版本限制”，随后要求使用当前 API 创建并加载世界。

**修改。** 在 `SessionAdmissionPolicy` 增加 `IgnoreProtocolVersion`，默认关闭；最小服务器的 `ServerComposition` 显式启用。准入阶段可跳过 Hello 中的通信版本字符串比较，继续执行既有认证、容量、密码及包边界检查。随后通过 `--create-world` 调用当前创建 API 并启动监听。

**结果与边界。** 服务器能够越过版本字符串不一致这一处限制。后续仍逐个修正了包格式和模块编号，说明跳过 `Terraria319` / `Terraria326` 比较只能放行握手，不能替代协议兼容工作。

证据：[准入策略](../../src/MinimalImplementation/Session/SessionAdmissionPolicy.cs)、[Host 组装](../../src/MinimalImplementation/Host/ServerComposition.cs)、[通信版本 CR](../cr/CR-2026-10-20-ignore-communication-version.md)。

### M02：增加能够定位断连原因的服务器日志

**现象。** 客户端只显示发现服务器、崩溃或连接丢失，原有服务端输出不足以判断停在哪个阶段。

**修改。** 加入带时间、级别和稳定事件名的日志，覆盖世界创建、读取、发布、监听、Tick、停止及保存结果；连接日志记录接入、远端、打开、关闭、关闭原因和最近序号。协议诊断逐步增加消息 ID、模块 ID、序号、帧长度、错误码及失败偏移，分别用于定位 Packet 82、27 和世界物品解码问题。

**结果与边界。** 后续故障从“客户端断了”收敛到了具体失败包和字段。Packet 82 诊断期间临时采集过精确失败体，定位后移除了临时采集；常规日志不输出密码、令牌或整段包内容。

证据：[日志入口](../../src/MinimalImplementation/Host/ServerLog.cs)、[连接 Host](../../src/MinimalImplementation/Host/ServerConnectionHost.cs)、[Packet 82 诊断日志](../../Build/runtime/ProtocolDisconnectDiagnostic-2026-10-21/server-326fix-1.out.log)。

### M03：修复“发现服务器4”阶段的世界元数据问题

**根因。** 初始创建流程使用 `WorldFileTreeTopsSection.Empty`，树顶区段为 0 项；入服 Packet 7 需要读取 13 项，导致世界数据构造或接收链路不能完成。早期排查提到的四项环境 `treeStyle` 是另一组数据，最终修复针对的是树顶区段。

**修改。** 新建世界时初始化 13 项树顶值，使保存数据与 Packet 7 的读取要求一致。

**结果与边界。** 新建世界的该项结构得到修复；早先已经生成的错误 `world.wld` 没有被宣称自动迁移，继续显式加载旧错误文件仍可能重现问题。后续成功入服还依赖其他协议修复。

证据：[世界创建协调器](../../src/MinimalImplementation/Persistence/WorldCreationCoordinator.cs)、[通信版本 CR 中的后续修复记录](../cr/CR-2026-10-20-ignore-communication-version.md)。

### M04：补齐最新客户端入服时的库存、装备上传

**根因。** 新客户端在分配玩家槽后、请求世界信息前，会发送 Packet 68、147 和批量 Packet 5。最小服务器缺少 5/68 路由，147 的库存读取范围也不完整，导致正常入服上传被拒绝。

**修改。** 在发出 Packet 3 前初始化 990 个库存槽，范围为 0—989；将 Packet 5 绑定到已认证的玩家身份处理；认证后消费 Packet 68，并让 147 读取完整库存与配装数据。

**结果与边界。** 后续最新客户端能够完成此阶段并进入世界。本轮核对以 `D:\TRbackup\最新的客户端` 中的 v1.4.5.8 / `Terraria326` 为主；早先 `D:\TRbackup\客户端` 中的 v1.4.5.6 / `Terraria319` 不能独立证明最新二进制布局。

证据：[入站路由](../../src/MinimalImplementation/Host/Version4InboundRouter.cs)、[配装处理](../../src/MinimalImplementation/Host/Version4InboundRouter.Loadout.cs)、[入服快照](../../src/MinimalImplementation/Host/Version4InboundRouter.JoinSnapshots.cs)。

### M06：修复无床出生坐标与错误的初始玩家位置

**根因与两次修正。** 原版客户端用 Packet 12 的 `SpawnX=-1, SpawnY=-1` 表示没有个人床位。第一轮修复允许这对哨兵值，同时拒绝不成对的非法负数，但当时只保留服务端已有位置。后来 NPC 排查发现，这可能保留 `(0,0)`，使出生前的活动范围计算将出生点史莱姆当作远处 NPC 清理。

**最终修改。** 保留 `-1/-1` 的协议语义，在 NPC 活动计算前解析世界出生点或队伍出生点，并按玩家尺寸换算位置。示例世界出生格 `(2095,232)` 对应玩家左上位置 `(33518,3670)`，不再依赖首次 Packet 13 才建立有效位置。

**验证。** 最终原生生命网络探针覆盖了“成对哨兵出生、尚未收到第一份控制包”的场景，确认初始 NPC 存活。普通远距离 NPC 退休的终止消息发送问题没有借此扩展完成。

证据：[玩家生命周期](../../src/MinimalImplementation/Player/PlayerLifecycleCoordinator.cs)、[玩家状态包处理](../../src/MinimalImplementation/Player/PlayerStatePacketHandlers.cs)、[玩家输出适配](../../src/MinimalImplementation/Host/Version4InboundRouter.PlayerOutput.cs)、[最终网络报告](../../Build/runtime/NpcAiDamage-B1-2026-10-22/report-native-network.json)。

### M07：修复连接后立即发生的原版客户端光照崩溃

**根因。** 初始占位世界只有 1×753 格。客户端收到 Packet 7 后进入 `TileLightScanner.ExportTo` / `LegacyLighting`，宽度为 1 导致扫描边界反转，最终出现 `CountdownEvent(initialCount)` 参数越界。

**修改。** 将新占位世界改为 4200×1200，设置匹配的中心出生点，并让空地形 RLE 与实际宽高一致。该阶段产生过 `world-4200x1200-client-crash-fix.wld`，文件版本为 326。

**结果与边界。** 修复了导致光照扫描崩溃的尺寸输入。该文件仍是空地形；后来“能够进入但世界空白”有独立原因，见 M09。

证据：[服务器创建运行时](../../src/MinimalImplementation/Host/P08BServerRuntime.cs)、[Tile 负载编码器](../../src/MinimalImplementation/World/WorldFileTilePayloadEncoder.cs)。

### M08：修复 Packet 82 模块编号错位导致的“连接已丢失”

**诊断证据。** 多轮在 `127.0.0.1:7781` 复现后，定位到序号 361 的 Packet 82：帧长 12 字节、负载 9 字节，模块体为 `0E00000000003F`，旧处理器读完后剩余 2 字节。剩余内容属于有效字段，不能当填充忽略。

**根因。** 最新客户端在模块 5 插入 `CreativeUnlocks`，使线上的模块 6 成为 `CreativePowers`；服务端旧逻辑把 6 当成献祭报告，因而用错解码器。

**修改。** 按 Steam 客户端模块注册表建立线上编号与既有逻辑处理器之间的入站映射及出站反向映射。关键编号为 `CreativePowers=6`、献祭报告 7、`CraftingRequests=12`；不再把自定义 `TagEffect` 占到原版模块 12。继续严格校验包体读尽。

**验证。** 用户明确反馈“成功进入世界”。此后出现的 40/13 拒绝日志没有被当成此次 Packet 82 断连的根因。

证据：[模块编解码](../../src/MinimalImplementation/Protocol/Version4ModuleCodecs.cs)、[协议配置](../../src/MinimalImplementation/Protocol/Version4WireProfile.cs)、[断连诊断过程](../../.agent-workplace/changes/2026-10-21-protocol-disconnect-hotfix-draft.md)、[修复运行日志](../../Build/runtime/ProtocolDisconnectDiagnostic-2026-10-21/server-326fix-1.out.log)。

## 4. 世界格式、生成与地形传输

### M05：将世界文件输出升级到 326，保留旧文件读取

**需求决策。** 用户将最初建议的“继续写 319”改为“升级 WorldFile 编码器至 326”，并确认按中度变更在当前任务实施。

**修改。** 将可写版本设为 326，保留受支持 319—326 文件的读取及保存升级路径；编码尾部按新版顺序补上 `DualDungeonsSeed`、`MoreLightningSeed`、`NoLightningSeed` 后再写 manifest。创建文档与生成结果投影也声明 326。

**边界。** 当时历史 WorldStorage 完整项目曾因已删除 ECS 引用出现 139 个错误、3 个警告；后续只接通最小生成链所需依赖，不能据此声称整个旧解决方案已经修复或通过构建。另有带 754 项 Tile facts 的生成存档与当前 753 项支持集不符，曾被拒绝读取，未记录通用兼容修复。

### M09：接入完整生成器，解决整个世界为空

**根因。** 4200×1200 占位文件的大小和版本已经合法，但创建 API 仍调用空地形编码，结果是 4200 列、每列 1200 格空气。升级 WorldFile 编号本身不会产生地形。

**实施范围。** 用户先允许加载既有 `test.wld` 的副本作为真实地形对照，随后明确选择“按重大变更接入完整生成器”和“本任务 + spec”。接入既有约 318 个源码文件的生成器，为最小实现补齐必要契约、生成器本地住房与统计支持，避免恢复已经移除的旧 ECS 运行时。

**修改。** 创建 API 执行完整生成、将结果投影为服务器支持的 WorldFile 文档，并复用服务器 Tile 编码器；投影包含地形、出生点、地层、宝箱、NPC 记录及受支持对象区段。两端都有 753 项规则，但家具初始化中的 14 项 frame-important 标记不一致，按最新客户端补齐。创建链还包含验证、原子写入、防覆盖和重读检查。

**结果。** 种子 `12345` 的一次生成完成 106 个 pass，用时约 54.04 秒，得到：

| 指标 | 结果 |
| --- | --- |
| 世界尺寸 | 4200×1200，共 5,040,000 格 |
| 实体方块 | 2,662,645 格 |
| 宝箱 | 174 个 |
| 文件内 NPC 记录 | 2 条；与后来诊断生成史莱姆、向导分别统计 |
| 出生格 | `(2095,232)` |
| 地表 / 岩层 | 331 / 427 |
| 创建 API 产物 | `FullGenerationServer-2026-10-21/generated-326.wld`，2,984,847 字节 |
| 独立投影探针产物 | `FullGenerationProjection-2026-10-21.wld`，2,984,854 字节 |

投影探针对 5,040,000 格比较得到 0 项不一致，并检查了重新编码稳定性。两个产物来自不同执行路径，大小分别记录，不能混用。该种子没有标牌和 TileEntity，无法据此确认这些区段存在非空内容时的行为。首次客户端复测仍空白或断连，直到 M10 修复液体启动问题后，用户才明确确认地形可见。

### M10：修复真实世界首次液体更新导致的退出

**根因。** 真实地形进入首个液体更新时，Host 缺少随机源适配器，抛出 `The host liquid random source is unavailable`。补上随机源后又暴露出初始化将全部液体及邻格入队、超过 75000 上限的问题。

**修改。** 提供 Host 液体随机源，仅将需要继续流动或更新的液体格加入初始队列。

### M12：修复使用任意武器导致的投射物包解码断连

**根因。** 用户反馈“所有武器”都会断连。实际失败为 Packet 27 的 `TrailingBytes`，偏移 26。最新客户端使用 Int32 `ProjectileKey` 表示含身份、归属和代际的信息，旧布局仍按 Int16 身份、单独 owner 及旧 UUID 扩展处理。

### M13：接通权威破坏、掉落与丢弃，修复客户端预测后复原

**现象。** 破坏蘑菇、普通方块没有掉落，重新进入后先前破坏消失；主动丢弃物品立即断开连接。

**地形根因及修改。** Packet 17 能解码，但 Host 没有相应处理，客户端只是本地预测破坏。补认证后的破坏路由，校验世界边界、已送达区块及支持规则；失败敲击只发效果，空格不重复生成掉落。实际删除与支持的掉落创建放在共享事务中提交，再通过 Packet 20 和物品投影同步。

**丢弃根因及修改。** 世界物品旧协议把 Packet 21 固定为 24 字节，新版按标志位附加 shimmer、敌方抓取等字段，导致尾部未读。对齐 Packet 21/22/39 和 151 退休流程；客户端实际先用槽 400 的 Packet 21 请求创建，再上传 Packet 5 库存扣减，服务端据此挂起请求、验证扣减，并原子分配服务端物品槽。

**结果与边界。** 后续日志出现真实地形删除、掉落创建、归属与拾取退休，最后的客户端复测也确认能够丢弃后再次拾取。物品投影已有 `PeriodicSync` 的 `ModulePeriodicSyncOwner` 消费链，不能将中间“没有排空投影”的怀疑作为最终缺失结论。

原始“重进后破坏复原”的无权威提交根因得到处理，但**同一进程内重新连接**与**保存后停止、重启再读盘**是不同验证项。后期使用独立世界副本并关闭停止保存，现有记录不足以签收磁盘持久化；不能将其写成重启不回档已确认。

### M18：处理 10 万血史莱姆受击粒子过量与击杀卡顿

**根因。** 原版客户端把普通史莱姆最大生命按原生值 25 处理，而 Packet 23 不能独立同步任意最大生命。服务端强行提高当前生命后，客户端受击粒子循环仍按 `damage / lifeMax * 100` 估算，例如伤害 1000 会产生约 4000 次循环，造成明显粒子和性能问题。

**最终选择。** 曾试图使用难度覆盖，但其生命倍率上限为 4，且会连带影响攻击和击退，后撤回。用户明确选择：

### M19：修复丢弃物品的拾取排除计时无法结束

**现象与定位。** 新掉落可正常拾取，某些自己丢弃的物品却无法重新拿起。旧 `7790` 日志先记录 type 71 铜币丢弃，随后多个物品没有退休记录。

**根因。** 丢弃创建了 100 帧的原丢弃者拾取排除时间，但计时与全部物品运动共用一个事务。未归属铜币需要的怪物拾取事实不可用，使整次物品运动更新失败，计时也不提交；归属选择又要等排除时间结束，形成循环依赖。这是源码和旧日志共同支持的判断，旧进程没有捕获到实时计数器。

**修改。** 增加 `WorldItemTickCoordinator.PrepareOwnershipTimerTick`。仅在碰撞事实或运动准备返回 `Unavailable` 时，通过已有物品、世界和归属修订保护提交抓取延迟、原主排除及预留计时；不伪造位移、物品或库存，不发送运动投影。正常运动成功时仍由原路径推进一次计时，避免重复扣减。延迟原因变化时记录 `server.item.motion.deferred`，实际分配归属记录 `server.item.owner_assigned`。

**部署与验证。** 修复版构建完成，0 警告、0 错误；另起 `127.0.0.1:7791`，使用独立 `world-copy.wld`，`SaveOnStop=false`。原 `7790` 仍为旧实例，没有原地替换。用户对“铜币和木材丢弃后再拾取”复测回答：

> 两种物品都能重新捡起

最新日志直接记录的是 type 129 灰砖和 type 9 木材创建、分配归属并退休。木材例子为 14:44:26.117 丢弃 21 个，14:44:27.777 分配归属，14:44:28.066 拾取退休。该日志没有铜币丢弃，也没有触发 `motion.deferred` 的记录，因此铜币成功依据用户反馈，不能写成日志已复现计时回退分支。其他物品及该分支的独立自动探针仍未覆盖。

证据：[计时准备与提交](../../src/MinimalImplementation/Inventory/State/WorldItemTickCoordinator.cs)、[Tick 调用](../../src/MinimalImplementation/Host/DefaultServerTickPhaseOwners.cs)、[物品归属选择](../../src/MinimalImplementation/Host/VanillaWorldItemOwnership.cs)、[拾取修复过程记录](../../.agent-workplace/changes/2026-10-22-dropped-item-pickup.md)、[构建日志](../../Build/runtime/item-pickup-server-build-final.log)、[实例信息](../../Build/runtime/ItemPickup-Live-2026-10-22/instance.json)、[客户端运行日志](../../Build/runtime/ItemPickup-Live-2026-10-22/server.stdout.log)。
