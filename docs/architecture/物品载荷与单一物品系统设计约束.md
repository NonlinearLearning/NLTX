本文件规定"物品"概念在 ECS 与运行时状态中的切分方式：哪一层持有身份与数量，哪一层持有驻留位置，
两种状态之间如何交接，以及哪些形态被禁止。它不规定具体物品数值、掉落表、网络包格式或界面表现。

## 2. 决定

物品概念收敛为**一层共享载荷 + 一个 Item 域 + 两种互斥状态**。合并的是状态归属与写者，
不是载荷定义。

```text
                共享载荷层（无 tick、无 owner、无世界字段）
                ItemId / ItemStack(ItemId, Quantity, Prefix)
                Item + ItemRegistry + ItemCategoryMask
                                │
                                ▼
                        Item 域（单一 owner、单一写者）
                   ItemState = ItemStack + Presence + Address
                   ItemStore：400 世界槽段 + 容器槽索引段
                   · 仅 ItemSystem 在 Commit 阶段可写
                                │
              ┌─────────────────┴─────────────────┐
              ▼                                   ▼
     Embodied（实体态，瞬态）              Dormant（非实体态，持久）
     Address = WorldSlot(index)            Address = ContainerSlot(container, index)
     · 槽号即网络身份（包 21/22/39）        · 随玩家/箱子存档
     · 位置、速度、归属预留、生命周期计数     · 只有槽位引用，数量仍在同一条记录上
     · 不写入任何存档                       · 无 tick，交互时读写
              └────────── 转移＝单次原子改址 ──────────┘
```

**为什么不是单一类型。** 原版 `Terraria.Item` 不继承 `Entity`，`Item.cs` 全文对 `position`/`velocity`
的引用全部落在 `worldItem.*` 上；而 `Terraria.WorldItem : Entity` 以组合方式持有一个 `Item inner`。
容器一侧（`Player.inventory`、`Chest.item`）的元素类型是 `Item[]`，世界一侧
（`Main.item`）是 `WorldItem[401]`。若把世界字段做进一个被容器逐格复制的类型，`Item.Clone()`（
`MemberwiseClone`）会连位置与预留一起复制。本设计因此不合并**类型**，只合并**域**。

**为什么不是两个各存身份的 store。** 载荷必须只有一份定义，且数量只能有一条权威记录。
合并后世界槽与容器槽都是**同一条记录的不同地址**，不再出现"世界侧扣多少、容器侧收多少"的
双写对账窗口。

## 3. 不变量

以下五条是设计的可判定内容。任何涉及物品状态的改动都必须保持它们：

| ID | 不变量 | 判定方式 |
| --- | --- | --- |
| INV-1 | **载荷唯一**：物品身份、数量、前缀只以 `ItemStack` 表达，不存在第二份权威副本 | 静态：不存在同义平铺字段；运行：同一记录在两段地址读出的三元组一致 |
| INV-2 | **地址唯一**：一条物品记录同一时刻恰好一个 `ItemAddress`，不存在游离态 | 运行：转移后地址数 == 记录数 |
| INV-3 | **单一写者**：只有 `ItemSystem` 在 Commit 阶段写 `ItemStore` | 静态：只读端口不暴露写入口 |
| INV-4 | **转移守恒**：改址前后总量守恒；部分成交时剩余 = 原量 − 实收 | 运行：部分成交后世界余量 == 原量 − 实收 |
| INV-5 | **瞬态/持久分离**：Embodied 记录不进入任何存档路径，Dormant 记录必须进入 | 静态：store 无 Embodied 写档 API |
| INV-6 | **状态字段隔离**：Embodied 专用字段只为 Embodied 记录读取 | 静态：属性只在 `Presence == Embodied` 分支可达 |

对应断言位于 `Test/Terraria.Components/Terraria.WorldItem`（`invariant-*` 前缀，9 条）与
`Test/Terraria.Components/Terraria.Inventory`（`slot-*` 前缀，5 条；手持关系并入容器后另加
`held-*` 前缀 7 条）。INV-2 与 INV-6 为合并引入的新不变量，断言随迁移批次 M2 补齐。

## 4. 各层的职责与禁止事项

| 层 | 负责 | 禁止 |
| --- | --- | --- |
| 载荷层 | 物品身份（`ItemId`）、数量、前缀、堆叠规则（`CanStackWith`）、内容定义（`MaxStack`、类别、属性修饰器） | 任何驻留状态（位置、速度、归属、寿命）；任何 tick 逻辑；持有 store 引用 |
| Item 域（Embodied） | 槽位身份（400 槽、槽号即网络身份）、位置与速度、归属预留（`ReservedFor`）、生命周期计数（`NoGrabDelay`/`OwnTime`/`KeepTime`/`TimeSinceItemSpawned`/`Shimmered`）、合并与拾取规则 | 写入存档；接受 `ItemSystem` 之外的写者；把世界字段暴露给 Dormant 读取方 |
| Item 域（Dormant） | 容器槽地址、槽位布局与容量、类别接收规则、值堆的插入/取出/转移 | 把 Dormant 记录写进任何世界存档之外的持久路径；复制第二份数量权威 |
| 容器域（Inventory） | 槽表结构、槽位类别定义、容量、手持槽索引 | 持有物品数量；持有世界槽号；把持手物品另存一份 |
| 使用配置 | 按 `ItemId` 注册的不可变使用档案（`UseTime`/`UseAmmo`/`ManaCost` 等） | 挂在物品实例上；依赖客户端上报的数值 |

### 4.1 手持概念由容器宿主表达

原版把"手上拿什么"写成一个派生读取而不是第二个存储：

```csharp
// 最新的客户端/Terraria/Player.cs:3835-3837
public int selectedItem => selectedItemState.Selected;
public Item HeldItem => inventory[selectedItem];

// 最新的客户端/Terraria/Player.cs:42925（ItemCheck 第一行）
Item item = inventory[selectedItem];
```

包 13 把同一个字节写进 `selectedItemState.Select(...)`（`MessageBuffer.cs:996`），包 5 则只写
`inventory[slot]`。也就是说"选中的槽"和"手上物品"是同一件事的两个视角，二者都不构成独立 owner。

本设计据此把手持关系放进容器域：

| 表达 | 位置 | 说明 |
| --- | --- | --- |
| 选中哪个槽 | `InventoryComponent.Held`（`HeldSlot?`） | `null` 即"没有手持任何槽" |
| 手持的物品 | `InventoryComponent.TryGetHeld()` | 直接返回该槽的 `ItemStack`，不复制 |
| 改选 / 读取 | `InventorySystem.TrySetHeldSlot` / `TryGetHeldStack` | 唯一写入口，非法槽号在提交前拒绝 |
| 输入来源 | 包 13 → `PlayerInputRequestKind.SelectHeldSlot` | 适配器只提交意图，不直接写库存 |

由此得到两条可判定的推论：手持载荷不进入第三份拷贝（INV-1），改选不搬运任何数量（INV-2）——
`Test/Terraria.Components/Terraria.Inventory` 的 `held-*` 断言与
`Terraria.ItemUse` 的 `use-without-held-slot-rejected` 覆盖这两点。

**不使用独立 `HandsComponent` 的原因**：它要求为"手上物品"再建一个地址，而本设计已把地址限定
为恰好一个（INV-2）。重建手部关系等于让同一条记录同时拥有槽地址与手地址，直接违反 INV-1/INV-2。

**载荷层不建模的东西**：`Item` 在原版里混合了定义（`damage`、`useTime`、`prefix` 规则）、
实例状态（`prefix`、`favorited`）与世界状态（由 `WorldItem` 承担）。本设计只把前三者中
"身份 + 数量 + 前缀"放进 `ItemStack`，把"按种类的规则"放进 `Item`/`ItemUse`。
其余字段在需要时按同一原则增补，不得回流到世界状态。

## 5. 两个宿主之间的交接

只有一个方向是"提议—回报"式，另一个方向由客户端上报。

### 5.1 世界 → 容器（拾取）

```text
WorldItemTickSystem.PickupPass
  → InventoryPickupRequest（世界侧提议：哪个槽、什么载荷、给谁）
  → InventoryPickupRequestSystem.TryInsert（容器侧决定实际接收多少）
  → WorldItemRequestKind.Consume（容器侧回报实收数量）
  → Commit 阶段 WorldItemRequestSystem 按回报数量扣减世界槽
```

关键在**容器只回报实收数量**，世界按该数量扣减。因此部分拾取既不复制也不吞物品。
这是 INV-4 的实现方式，不是事后核对。

拾取门控顺序与 Version4 一致：`Player.GetItem(WorldItem, …)` 在 `noGrabDelay > 0` 时直接返回原物品，
连"能否装下"都不判断。本设计把该判定提前到候选筛选（`WorldItemRules.CanBePickedUp`），
并在 tick 末尾统一递减计数——**先判定后递减**，否则刚生成的物品会在同一 tick 少掉一格延迟。

### 5.2 容器 → 世界（丢弃）

**不是服务端移交系统。** Version4 的丢弃由客户端本地 `Item.NewItem` 创建世界物品后广播包 21 完成；
服务端收到 `num == 400` 时**自行重新分配槽位**（`MessageBuffer.cs:1485-1492`），客户端给的 400
只是"请新建"的哨兵。

因此本设计只要求：`WorldItemRequestKind.Create` 的 `Slot` 是哨兵，世界宿主**忽略它并自行分配**
（取最低空闲槽）。不得把该参数当作客户端的槽位授权。

## 6. 调度与提交顺序

状态归属决定提交点，不决定执行顺序；顺序必须显式声明，不得依赖目录或注册顺序的巧合。

| 约束 | 理由 |
| --- | --- |
| 世界 tick 晚于世界时钟推进 | 物品物理跟随世界时间 |
| 拾取结算紧随世界 tick | 同 tick 产生的拾取事实必须在本 tick 内结算完 |
| 世界物品请求只在 Commit 阶段执行 | 权威 store 只在 Commit barrier 被写；Projection 产生的请求留到下一 tick |
| 世界网络投影在 Commit 之后 | 投影只观察已提交状态，不回写 |

已知窗口（迁移完成前）：拾取在 Simulation 阶段写容器、`Consume` 在 Commit 阶段扣世界，两者之间
同时读两侧的系统会看到"背包已加、世界未减"。设计要求：**任何跨状态读取都必须在 Commit 之后**；
迁移批次 M2 完成后该窗口消失（单条记录改址，只有一个提交点）。若 M2 前确有系统必须在该窗口内
读两侧，则需把拾取结算整体移入 Commit，而不是放宽不变量。

## 7. 当前实现与已知缺口

| 项 | 状态 |
| --- | --- |
| 载荷层 | `Share/Item/ItemStack`、`Item`、`ItemRegistry`、`ItemId` |
| Item 域 | `Item/ItemSystem`（唯一提交写者）、`Item/ItemTickSystem`（Embodied 物理）、`Item/System/ItemStore`（`_worldSlots` 400 槽 + `_containerSlots` 地址索引）、`ItemState`（记录 + `Presence` + 地址）—— **已迁移** |
| 容器域 | `Share/Inventory/InventorySystem`、`InventoryComponent`、`InventorySlot`（`Content` 存 `ItemContainerAddress?` 地址，不存载荷） |
| 手持关系 | `InventoryComponent.Held` + `HeldSlot`：只是库存里的一个索引，载荷仍是被选中的那一格（见 §4.1） |
| 使用配置 | `Share/ItemUse/Content/ItemUse` 等 |
| 物品实体路径 | **已删除**（`ItemStackComponent`、`ItemWorldStateComponent`、`ContainedInInventoryComponent`、`InventorySlot.ItemEntityId`） |
| 世界侧 `MaxStack` 校验 | **仍缺失**。`ItemStore.TryCreate` 只校验类型已知、`stack > 0`、坐标有限，不校验定义的 `MaxStack`。客户端包 21 可造出超上限的世界堆，容器整堆拒绝后该堆永不可拾取，只能等 `KeepTime` 或出界退役。不复制、不丢失，但会卡住物品 |

**已删除能力**："物品实体自带子库存"（如枪械内置弹药库）当前无容器表达。合并为单域后该能力
重新可表达——Dormant 记录可以挂子容器地址（见设计文档 §9），无需先让物品成为世界实体。
但仍**不得恢复一条无生产者的声明**：能力须随迁移批次 M0–M4 一并落地。

## 8. 新增物品行为时的检查清单

- [ ] 新增字段是否属于"载荷 / 状态（Embodied / Dormant）/ 容器布局 / 内容定义"中的恰好一层？跨层就说明切错了。
- [ ] 是否把物品身份平铺成 `type`/`stack`/`prefix` 字段，形成第二份权威？
- [ ] 是否出现既不在世界槽也不在容器槽的"游离"记录（违反 INV-2）？
- [ ] Embodied 专用字段是否可能被 Dormant 记录读到（违反 INV-6）？
- [ ] 跨状态动作是否在单次提交内完成改址，并回报实际成交数量？
- [ ] 新写者是否绕过 `ItemSystem`（迁移完成前为 `WorldItemRequestSystem` + `InventorySystem` 两处）？
- [ ] 是否给只读端口加了写方法？
- [ ] Embodied 记录是否被写进了任何存档路径？
- [ ] 新计数是否放在 tick 末尾递减，以保持"先判定后递减"？
- [ ] 相应 `invariant-*` / `slot-*` / `held-*` 断言是否仍然全绿？
- [ ] 需要"手上物品"时是否经 `InventoryComponent.TryGetHeld` 读取，而不是新开一个存储？
