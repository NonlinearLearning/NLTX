本文件规定"物品"概念在 ECS 与运行时状态中的切分方式：哪一层持有身份与数量，哪一层持有世界位置，
两个宿主之间如何交接，以及哪些形态被禁止。它不规定具体物品数值、掉落表、网络包格式或界面表现。

## 2. 决定

物品概念拆为**一层共享载荷 + 两个互斥宿主 owner**，而不是两个各自管理物品的系统。

```text
                共享载荷层（无 tick、无 owner、无世界字段）
                ItemId / ItemStack(ItemId, Quantity, Prefix)
                Item + ItemRegistry + ItemCategoryMask
                                │
            ┌───────────────────┴───────────────────┐
            ▼                                       ▼
      世界宿主（瞬态）                        容器宿主（持久）
      WorldItemStore + WorldItemState          InventoryComponent + InventorySlot
      · 400 槽运行时表，槽号即网络身份           · 随玩家/箱子存档
      · 位置、速度、归属预留、生命周期计数        · 只存 ItemStack 值
      · 不写入任何存档                          · Content == null 即空槽
      · 仅 WorldItemRequestSystem 可写          · 仅 InventorySystem 可写
            └────────── 移交只经请求组件，有方向 ──────────┘
```

**为什么不是单一类型。** 原版 `Terraria.Item` 不继承 `Entity`，`Item.cs` 全文对 `position`/`velocity`
的引用全部落在 `worldItem.*` 上；而 `Terraria.WorldItem : Entity` 以组合方式持有一个 `Item inner`。
容器一侧（`Player.inventory`、`Chest.item`）的元素类型是 `Item[]`，世界一侧
（`Main.item`）是 `WorldItem[401]`。世界物品不入世界文件，容器物品逐槽写盘。两条生命周期
互斥：一条每 tick 只在 400 槽上跑物理，一条只在交互时按槽位读写并持久化。

**为什么不是两个各存身份的 store。** 载荷必须只有一份定义。世界侧持有 `WorldItemState.Item`，
容器侧持有 `InventorySlot.Content`，两者都是同一个 `ItemStack` 值类型；不得各自平铺
`type`/`stack`/`prefix` 字段。

## 3. 不变量

以下五条是设计的可判定内容。任何涉及物品状态的改动都必须保持它们：

| ID | 不变量 | 判定方式 |
| --- | --- | --- |
| INV-1 | **载荷唯一**：物品身份、数量、前缀只以 `ItemStack` 表达，不存在第二份权威副本 | 静态：不存在同义平铺字段；运行：跨宿主读出的三元组一致 |
| INV-2 | **宿主互斥**：同一 `ItemStack` 在同一时刻只被一个宿主拥有 | 运行：移交前后两侧总量守恒 |
| INV-3 | **单一写者**：世界槽只由 `WorldItemRequestSystem` 在 Commit 阶段写；容器槽只由 `InventorySystem` 在提交阶段写 | 静态：只读端口不暴露写入口 |
| INV-4 | **转移守恒**：容器实收数量 == 世界扣除数量 | 运行：部分成交时世界余量 = 原量 − 实收 |
| INV-5 | **瞬态/持久分离**：世界物品不进入任何存档路径，容器物品必须进入 | 静态：世界 store 无存档型 API |

对应断言位于 `Test/Terraria.Components/Terraria.WorldItem`（`invariant-*` 前缀，9 条）与
`Test/Terraria.Components/Terraria.Inventory`（`slot-*` 前缀，5 条）。

## 4. 各层的职责与禁止事项

| 层 | 负责 | 禁止 |
| --- | --- | --- |
| 载荷层 | 物品身份（`ItemId`）、数量、前缀、堆叠规则（`CanStackWith`）、内容定义（`MaxStack`、类别、属性修饰器） | 任何世界状态（位置、速度、归属、寿命）；任何 tick 逻辑；持有容器或世界 store 引用 |
| 世界宿主 | 槽位身份（400 槽、槽号即网络身份）、位置与速度、归属预留（`ReservedFor`）、生命周期计数（`NoGrabDelay`/`OwnTime`/`KeepTime`/`TimeSinceItemSpawned`/`Shimmered`）、合并与拾取规则 | 写入存档；被容器直接引用；接受宿主注入之外的写者 |
| 容器宿主 | 槽位布局与容量、类别接收规则、值堆的插入/取出/转移 | 持有世界槽号；调用世界 store；跨域直接写世界状态 |
| 使用配置 | 按 `ItemId` 注册的不可变使用档案（`UseTime`/`UseAmmo`/`ManaCost` 等） | 挂在物品实例上；依赖客户端上报的数值 |

**载荷层不建模的东西**：`Item` 在原版里混合了定义（`damage`、`useTime`、`prefix` 规则）、
实例状态（`prefix`、`favorited`）与世界状态（由 `WorldItem` 承担）。本设计只把前三者中
"身份 + 数量 + 前缀"放进 `ItemStack`，把"按种类的规则"放进 `Item`/`ItemUse`。
其余字段在需要时按同一原则增补，不得回流到世界状态。

## 5. 两个宿主之间的交接

只有一个方向是"提议—回报"式，另一个方向由客户端上报。

### 5.1 世界 → 容器（拾取）

```text
WorldItemTickSystem.PickupPass
  → InventoryPickupRequest（世界侧提议：哪个槽、什么载荷、给谁）
  → InventoryPickupRequestSystem.TryInsert（容器侧决定实际接收多少）
  → WorldItemRequestKind.Consume（容器侧回报实收数量）
  → Commit 阶段 WorldItemRequestSystem 按回报数量扣减世界槽
```

关键在**容器只回报实收数量**，世界按该数量扣减。因此部分拾取既不复制也不吞物品。
这是 INV-4 的实现方式，不是事后核对。

拾取门控顺序与 Version4 一致：`Player.GetItem(WorldItem, …)` 在 `noGrabDelay > 0` 时直接返回原物品，
连"能否装下"都不判断。本设计把该判定提前到候选筛选（`WorldItemRules.CanBePickedUp`），
并在 tick 末尾统一递减计数——**先判定后递减**，否则刚生成的物品会在同一 tick 少掉一格延迟。

### 5.2 容器 → 世界（丢弃）

**不是服务端移交系统。** Version4 的丢弃由客户端本地 `Item.NewItem` 创建世界物品后广播包 21 完成；
服务端收到 `num == 400` 时**自行重新分配槽位**（`MessageBuffer.cs:1485-1492`），客户端给的 400
只是"请新建"的哨兵。

因此本设计只要求：`WorldItemRequestKind.Create` 的 `Slot` 是哨兵，世界宿主**忽略它并自行分配**
（取最低空闲槽）。不得把该参数当作客户端的槽位授权。

## 6. 调度与提交顺序

状态归属决定提交点，不决定执行顺序；顺序必须显式声明，不得依赖目录或注册顺序的巧合。

| 约束 | 理由 |
| --- | --- |
| 世界 tick 晚于世界时钟推进 | 物品物理跟随世界时间 |
| 拾取结算紧随世界 tick | 同 tick 产生的拾取事实必须在本 tick 内结算完 |
| 世界物品请求只在 Commit 阶段执行 | 权威 store 只在 Commit barrier 被写；Projection 产生的请求留到下一 tick |
| 世界网络投影在 Commit 之后 | 投影只观察已提交状态，不回写 |

已知窗口：拾取在 Simulation 阶段写容器、`Consume` 在 Commit 阶段扣世界，两者之间同时读两侧的系统
会看到"背包已加、世界未减"。设计要求：**任何跨宿主读取都必须在 Commit 之后**。若将来出现
必须在该窗口内读两侧的系统，则需把拾取结算整体移入 Commit，而不是放宽不变量。

## 7. 当前实现与已知缺口

| 项 | 状态 |
| --- | --- |
| 载荷层 | `Share/Item/ItemStack`、`Item`、`ItemRegistry`、`ItemId` |
| 世界宿主 | `WorldItem/System/WorldItemStore`（400 槽）、`WorldItemState`（6 个位置参数 + 5 个生命周期 `init` 属性） |
| 容器宿主 | `Share/Inventory/InventorySystem`、`InventoryComponent`、`InventorySlot`（值或空槽） |
| 使用配置 | `Share/ItemUse/Content/ItemUse` 等 |
| 物品实体路径 | **已删除**（`ItemStackComponent`、`ItemWorldStateComponent`、`ContainedInInventoryComponent`、`InventorySlot.ItemEntityId`） |
| 世界侧 `MaxStack` 校验 | **缺失**。`WorldItemStore.TryCreate` 只校验类型已知、`stack > 0`、坐标有限，不校验定义的 `MaxStack`。客户端包 21 可造出超上限的世界堆，容器整堆拒绝后该堆永不可拾取，只能等 `keepTime` 或出界退役。不复制、不丢失，但会卡住物品 |

**已删除能力**："物品实体自带子库存"（如枪械内置弹药库）不再有容器表达。当前仓库无此类内容。
若将来需要，必须按执行计划 P1-B 重新设计（世界物品改走 ECS 实体、`WorldItemStore` 降为投影索引），
**不得恢复一条无生产者的声明**。

## 8. 新增物品行为时的检查清单

- [ ] 新增字段是否属于"载荷 / 世界 / 容器 / 内容定义"中的恰好一层？跨层就说明切错了。
- [ ] 是否把物品身份平铺成 `type`/`stack`/`prefix` 字段，形成第二份权威？
- [ ] 跨宿主动作是否走请求组件，并回报实际成交数量？
- [ ] 新写者是否绕过 `WorldItemRequestSystem`（世界）或 `InventorySystem`（容器）？
- [ ] 是否给只读端口加了写方法？
- [ ] 世界物品是否被写进了任何存档路径？
- [ ] 新计数是否放在 tick 末尾递减，以保持"先判定后递减"？
- [ ] 相应 `invariant-*` / `slot-*` 断言是否仍然全绿？
