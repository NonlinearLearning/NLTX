# 液体更新与 tick 预算优化计划

**文档 ID**：PLAN-2026-11-22-LIQUID-TICK-BUDGET  
**策略**：sequential（先定位、再收敛、后限流；每步都有可判定的观测量）  
**状态**：in-progress（液体收敛已落地并初步验证；soak 与预算统一尚未收口）  
**关联变更**：[CR-2026-11-22 NPC 同步出站优先级隔离](../cr/CR-2026-11-22-npc-sync-outbound-priority.md)、[出站 tick 批执行计划](../plans/2026-11-22-outbound-tick-batch-execution-plan.md)  
**范围**：`src/NSSLC/Physics/Liquid/**`（液体推进与入队）、服务端 tick 预算常量  
**排除范围**：`src/NSSLC.Infrastructure/**` 只读；不改协议格式与包号；不改客户端；不改 `ServerTickPacing` 的网格语义（错过即丢弃、不补发）。

## 1. 优化思路（用户提出）

四条思路按提出顺序记录，本计划以它们为唯一设计来源：

1. **分类出站数据**：每 tick 必须同步的数据在 tick 时刻立即发送；非每 tick 必须同步的数据共享一条队列；到固定 tick 时立即放弃当前非必须数据，改发必须数据，发完再继续。
   （已由 [出站 tick 批执行计划](../plans/2026-11-22-outbound-tick-batch-execution-plan.md) 落地。）
2. **只发变化的数据**：世界数据同步只有发生改变的数据才发送。
3. **只算需要流动的液体**：只有需要流动的 liquid 才被更新；所有 tick 预算压低到 10% tick 占用。
4. **绝不跨期**：第 N tick 的必须同步批不得在第 N+1 tick 开始之后才写出。

## 2. 为什么需要这份计划（实测证据）

在一次 `科研.wld` 的 10 秒运行中，逐层定位得到的结论：

| 观测 | 数值 | 说明 |
| --- | --- | --- |
| 出站字节率 | 116.9 KB/s | 包 20 占 92.2 KB/s、包 10 占 21.0 KB/s、包 23 占 3.6 KB/s |
| 出站帧数 | 6,400 帧/秒 | 包 20 恒 15 B/帧，即一格一帧 |
| `network.world.projection` | 0.04 ms/tick | 生成全部 Tile 意图的投影阶段几乎不耗时 |
| `Simulation` 阶段 | 12.1–17.5 ms/tick | 占 `Update` 总耗时 96–98% |
| `AdvanceTick`（世界时间） | 0.00–0.02 ms/tick | 可以忽略 |
| `AdvanceLiquidSimulation` | 11.75–17.28 ms/tick | 占 `Simulation` 的 98% |
| `liquidOps` | 2,579–2,713，恒定不衰减 | 说明队列入不敷出、稳态饱和 |

由此确认：**掉 tick 的出站数据量大是同一根因的两个症状，而不是因果关系。** 液体每 tick 都在跑满预算，产生的 Tile 变化又变成海量出站帧。

根因在于液体均衡的收敛性：总额除以参与格数会产生余数，而余数按“源优先”分配，于是相邻两格 1 单位的差值会在两格之间反复倒手；每次倒手都算作变化，又触发邻居入队，队列因此永远清不空。

## 3. 工作项

### L0 只算需要流动的液体（已落地）

**做法**：

- 液面差 ≤1 时不执行水平搬运。这类格子即使参与均衡也不会产生搬运，只会触发下一轮入队。
- 新增「是否需要流动」判定：下方可容纳，或水平方向液面差 ≥2，二者之一成立才算需要流动。
- 该判定用于两处：入队时过滤（`EnqueueIfNeeded`），处理时兜底跳过。

**验收**：`liquidOps` 从恒定饱和转为可衰减；`tick_slow` 显著减少。

### L1 tick 预算压到 10%（部分落地）

**做法**：液体每 tick 操作上限由 3,500 降到 350。按实测每操作约 4.8 µs 折算，350 次约 1.7 ms，约等于 16.67 ms 的 10%。

**验收**：单 tick 内液体耗时 ≤1.7 ms，且不影响其他阶段的预算。

**未完成**：其他阶段的预算尚未统一到 10% 口径，目前只有液体一项。

### L2 绝不跨期（已建立度量并达标，机制兜底未做）

**做法**：利用既有批语义测量跨期——闭合标记排在本批帧之后进入同一条有序通道，写线程取到该标记的时刻就等于本批最后一帧写完的时刻，与一个 tick 周期比对即可判定跨期。

**已建度量**：`ecs.outbound.timeliness`，每秒最多一条，输出 `sealed` / `overdue` / `overdueRatio` / `maxLatencyMs`。

**未完成**：超期丢弃机制（计划 P1 latest-wins）尚未实现。当前跨期率为 0，属“负载足够低”的自然达标，不是机制保证。

### L3 只发变化的数据（现状确认，无需改动）

现有实现已满足：每 tick 取最多 128 条变更，按坐标去重后仅在有变更时发送。本项作为现状记录，不产生代码改动。

## 5. 未闭合项

1. **`tileUpdates` 反而上升**：同一时长内由约 38,400 增至 88,919（约 2.3 倍），尚未定位是“积压变更被完整排出”还是新判定导致的重复入队。判定条件：60 秒 soak 后该值应随时间衰减并趋于稳定，否则视为缺陷。
2. **预算 10% 只覆盖液体一项**，其他阶段未纳入统一口径。判定条件：各阶段实测耗时均 ≤1.67 ms，或书面说明某阶段为何允许超出。
3. **跨期率 0% 是负载余量的结果，不是机制保证**。判定条件：实现超期丢弃后，在高负载（液体预算调回 3500 或 50 连接）下跨期率仍为 0。
4. **视觉正确性未验**：液面差 ≤1 停止搬运会改变液体凝固的最终形态，需要用户用最新客户端确认可接受。

## 6. 测量方法要求

- 单次 6 秒采样的方差足以反转结论（已验证过：同一配置内 ≥25 ms 间隔次数在 69/197/187 之间波动）。任何节拍对比至少重复 3 次并报中位数。
- 阶段与系统级耗时取自 `ecs.server.tick_slow` 日志中的 `prep` / `sim` / `commit` / `proj` 与 `top=[...]`、`clock` / `liquid` / `liquidOps` 字段，均按 ≤1 条/秒节流。
- 跨期率取自 `ecs.outbound.timeliness`。
- 出站字节与帧数取自 `HeadlessPacketProxy` 抓包日志。
