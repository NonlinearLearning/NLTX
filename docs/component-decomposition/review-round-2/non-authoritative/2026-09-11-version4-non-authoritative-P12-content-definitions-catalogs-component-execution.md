## 2. Implementation order

1. Freeze source-member coverage and identity matrix; add no code until P12-MemberCoverage is independently reviewed.
2. Establish proposed content ID and SetArrayFactory ports, then build immutable colors, validation definitions and ability/prefix masks.
3. Build proposed ContentSampleIndexCatalog and derived Creative/Bestiary indexes only after sample clear/rebuild and persistent/network ID policy is approved.
4. Register proposed TileObject inheritance, geometry, placement, hook and style definitions in explicit phases; lock the definition catalog before runtime queries.
5. Build proposed ItemVariant, ArmorSetBonus and WingStats definitions and pure queries; keep Item/Player instance application outside P12.
6. Add proposed item static capability indexes and cache adapters; verify reset/invalidation and display-doll reverse lookup.
7. Add presentation/service adapters and projections; only then expose read-only compatibility facades.
8. Remove legacy writers only after owner, snapshot, network/persistence and focused verifier gates pass; this session does not authorize deletion.

Proposed dependency order: `SetArrayFactory -> definitions -> ContentSampleIndex -> derived lookups -> pure Queries -> Commands/Adapters/Projections`. Tile/World, Item, Player, UI, Network and Persistence commit order remains `crossSubsystemOwner: integration-review`.

## 3. Single-writer and compatibility strategy

- Each proposed catalog has one proposed registration/build System. Query consumers receive immutable/read-only views and cannot mutate arrays, dictionaries or external handles.
- During migration, the legacy surface may remain a read-only facade over the proposed owner. Bidirectional synchronization and independent double writers are prohibited.
- No dual write is executed in this session. A temporary compatibility adapter may mirror a typed projection only after a verifier proves ordering, failure handling and idempotence; the legacy writer must remain disabled or read-only.
- Tile placement hooks emit proposed commands; WorldGrid/TileEntity ownership is not assigned here. ArmorSetEffect and wing/item/player effects remain external commit seams.
- Caches (`cachedItemSpawnsByType`, `_phaseColors`, derived lookup dictionaries) require explicit invalidation; cache contents cannot be persisted as authoritative component state.

## 5. Network, persistence, snapshot and external migration

- Definition catalogs are not automatically replicated or persisted. When required, proposed `ContentDefinitionSnapshot`/`ContentIndexProjection` values must use stable versioned keys and retain local type, persistent ID and network ID as separate fields.
- Proposed network projection is read-only from committed catalog state; network input becomes a command. Unknown IDs, missing definitions and version mismatch produce explicit rejection/fallback results, not partial catalog mutation.
- Proposed persistence adapter writes typed definitions or stable references only after a validated snapshot. It must not serialize `Asset<T>`, Texture2D, shader handles, service instances, delegates, lock objects or transient query payloads.
- ContentSamples sample objects, TileObjectData registration scratch, SetFactory queues, `ArmorSetBonus.Builder`, QueryContext/Result, random style input, service handles and presentation caches are transient or derived and are excluded unless integration-review approves a typed projection.
- Existing NLTX `ContentCatalogSnapshot` is current partial structure, not migration evidence. Any reuse requires explicit field-by-field mapping and snapshot compatibility tests.

## 6. Rollback and failure conditions

Rollback is a proposed implementation action and was not performed. Disable the new adapter/owner and restore the read-only legacy facade as the sole reader/writer path when any gate observes:

- a second writer or a writer that bypasses the proposed command/adapter boundary;
- changed ContentSamples clear/rebuild results, ID mapping, sorting order or lookup ordering;
- TileObject copy/alternate/style/placement geometry drift, hook order drift or direct world mutation;
- changed variant/prefix/armor/wing selection, missing default, invalid ID handling or player-instance contamination;
- snapshot bytes, network IDs, persistent IDs or unknown-field behavior drift;
- cache leakage across reload/world teardown, external asset leak, failed retry duplication or non-idempotent placement;
- compile/test/static verifier failure once implementation begins.

Rollback does not mean deleting files, resetting the worktree, editing the runner ledger or changing the session ID.
