## 6. Compatibility and dual-write strategy

No dual-write or migration has run. If implementation is approved:

- first create proposed read-only adapters over legacy declarations and compare source revisions;
- introduce one proposed owner per state, with legacy reads routed through the owner or a compatibility
  projection;
- use proposed dual-read comparison in development builds for camera matrices, SceneMetrics
  aggregates, light colors, map tile packed bits, shader lookup, and draw command counts;
- permit at most one write path. During a bounded transition, a proposed compatibility adapter may
  mirror owner output to legacy consumers, but legacy code must not write back;
- for map/persistence, write a versioned proposed snapshot to a temporary path, validate checksum and
  decode, then atomically replace the durable document; rollback keeps the previous document;
- remove compatibility mirrors only after focused verifiers, integration review, and serial build
  evidence are recorded.

A mismatch, duplicate write, stale revision, or unbounded compatibility read is a stop condition.

## 7. Network, snapshot, and persistence strategy

Network:

- camera matrices, lighting caches, shader parameters, draw commands, vertex buffers, pings, and
  graphics handles remain client-local proposed projections unless integration review explicitly
  defines a network view;
- map tile snapshots may be published through a proposed network projection using separate network
  snapshot revision and world tile revision; source identity and protocol ownership are
  crossSubsystemOwner: integration-review;
- entity/player/projectile references in camera, drone, scene scan, and shadows use proposed immutable
  snapshots, never mutable simulation objects across adapters;
- no render cache is serialized as gameplay authority.

Persistence:

- proposed MapSaveProjection reads a stable C13 map snapshot; it never calls file I/O from an ECS
  query or render submit;
- proposed MapPersistenceAdapter owns IOLock, stream, compression, cloud/path policy, logging,
  retry, and atomic replacement;
- proposed C16 preserves legacy bit positions/reserved bits/option limits until compatibility
  evidence approves a versioned change;
- map file identity, world persistent identity, tile coordinate, and entity ID remain separate.

Snapshot publication:

- each snapshot carries a source revision, coordinate/map bounds where applicable, and capture tick;
- publication is immutable; consumers reject stale revisions according to integration policy;
- failure to publish a client projection does not mutate world/entity authority.

## 8. Rollback conditions and procedure

Rollback is required if any of the following occurs:

- a source member cannot be assigned without moving authority across a partition;
- camera or matrix output is non-finite, differs outside an approved tolerance, or invalidation loops;
- scene counters are not reset atomically, or a query mutates a component;
- active lighting reads working buffers, mode switch leaks old resources, or brightness is unclamped;
- draw commands escape a frame, submit twice, reference an invalid shader handle, or write authority;
- map packed bits fail round-trip, queue overflow changes authoritative tile state, or save corruption
  replaces the previous durable document;
- network/persistence IDs collide or a projection is interpreted as server authority;
- any proposed compatibility bridge introduces a second writer or cannot be disabled independently.

Procedure:

1. stop the affected proposed system at its last verified checkpoint;
2. disable the proposed adapter/projection and restore the previous read path;
3. retain the prior durable map document and old compatibility schema;
4. compare revision-tagged snapshots and record the first divergent source member;
5. remove only the transition branch after integration review; do not delete unrelated user work;
6. rerun focused verifiers and the required serial build before resuming.
