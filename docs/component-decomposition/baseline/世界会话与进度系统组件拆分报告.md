# 世界会话与进度系统组件拆分报告

> 依据 `public-decomposition` 的 ECS 证据协议编写。本轮已按该 skill 的本地文档补全上下文、字段级证据、模块契约和验证边界。本文不声称 Version4 已完成迁移；`src/WorldSession` 的状态类型和 `dome` 的世界规则验证是 NLTX 当前实现事实，二者不能被误称为对 Version4 静态状态的完整替换。

## 1. 范围与结论

本次先核对 `docs/Version4权威游戏模拟系统主要子系统.md` 中的“物品、容器与经济事务”边界，再追踪真实代码中的“世界会话与进度”来源，并使用 SS14 的 ECS 粒度作为组织参考。

结论如下：

1. Version4 的世界会话不是一个现成类，而是由 `Main` 的世界描述/规则/时间天气/入侵字段、`WorldGen` 的生成与世界标记、`NPC` 的 Boss/救援进度、`Terraria.GameContent.Events` 的事件状态，以及 `WorldFile` 的存档协议共同组成。
2. NLTX 已有 `src/WorldSession/WorldSessionComponents.cs` 的五个状态类型：`WorldDescriptorState`、`WorldRulesState`、`WorldTimeWeatherState`、`WorldEventProgressState` 与 `WorldSpawnPressureState`。它们是恰当的第一层聚合，不应再被拆为“每个 bool 一个组件”；但尚无将这些类型接入 Version4 的运行时 System/Adapter 证据。
3. 事件进度必须与 NPC 实例分离；`NPC.downed*`、`NPC.saved*` 是世界级持久进度。事件运行时计时器、波次、临时伤害归因则属于事件规则实体或事件组件。
4. SS14 的 `GameTicker` 提供可迁移的边界模式：回合状态、规则选择、规则激活/结束、玩家会话和地图加载分别由 partial/System/Component 表达；但 SS14 是“每回合重置”的站点游戏，并没有 Terraria 式跨回合世界存档，因此只能借鉴边界，不能照搬语义。
5. “物品、容器与经济事务”应消费只读的世界规则/进度视图（例如 hardmode、事件解锁、旅行商店时间），交易本身仍由 `CommerceTransactionSystem` 原子地写入库存/容器/货币，不能反向写世界会话字段。

### 3.1 明确不归入 WorldSession 的成员

- `Main.player/npc/projectile/item/chest`：属于 `WorldStorage`/实体槽位或容器存储。
- `Main.myPlayer`、相机、UI、网络发送计数：属于玩家会话或表现/协议投影。
- `WorldGen.tileCounts`、SceneMetrics 扫描结果、背景透明度：派生缓存；必须声明失效条件，不能成为世界进度权威。
- `DD2Event._damageTracker`、`MoonlordDeathDrama` 的爆炸/粒子对象：表现或伤害归因运行态，不是跨会话进度。
- 物品堆叠、库存槽、箱子内容、商店库存和货币余额：属于文档第 12 项的物品/容器/经济域；只能读取世界规则视图。

## 4. 目标组件与 System 边界

### 4.1 WorldSession 单例实体

每个世界应有一个受保护的 `WorldSession` 实体。NLTX 已定义的五个一级状态类型就是第一层组件边界；其内部结构和值对象再承载细粒度差异。以下 `Interface` 和 System 是目标契约，除另有说明外不代表已经接线。

| 现有一级组件 | 权威数据与内部边界 | 写入者 | 只读消费者 |
| --- | --- | --- | --- |
| `WorldDescriptorState` | 身份、种子文本、尺寸/地层、出生点/地牢、`PreparationState`；不将存档版本缓存混入其中 | Load/Generation System | 地图、刷怪、Persistence/Network Projection |
| `WorldRulesState` | 游戏模式、hardmode、秘密种子、邪恶类型、感染、矿层、祭坛/暗影珠里程碑 | 规则/进度命令与加载适配器 | NPC、掉落、物品资格、事件 Query |
| `WorldTimeWeatherState` | Clock、月相、天气/风、Slime Rain、血月/日食及 Birthday/Lantern/Sandstorm 的持久部分 | Clock/Weather System | 场景、刷怪、事件、时钟/网络 Projection |
| `WorldEventProgressState` | Boss、入侵、救援/城镇解锁、Lunar、入侵运行态、DD2 进度、待执行事件 | Progress/事件 System | NPC 服务、掉落、配方、经济资格、存档 Projection |
| `WorldSpawnPressureState` | spawn delay/period、城镇 NPC 检查、事件刷怪预算；活跃玩家数为派生读取 | Spawn System | NPC Spawn Query、事件资格 |

`InvasionRuntimeState`、`Dd2ProgressState` 与 `PendingWorldEventsState` 已是 `WorldEventProgressState` 的值子结构；不再提升为额外一级组件。DD2 单次波次、竞技场对象和伤害归因须放在 DD2 事件规则实体上，不能塞入跨会话快照。

### 4.2 模块契约与深度

| 模块 | Interface | Implementation | Seam | Depth | Leverage | Locality |
| --- | --- | --- | --- | --- | --- |
| 世界描述/生命周期 | `IWorldSessionView` | `WorldDescriptorState` + Load/Generation System | typed load snapshot 与 `PreparationState` 屏障 | 隐藏 WorldFile 二进制、生成期和边界坐标 | 地图、刷怪、网络共用一个描述视图 | `src/WorldSession`；加载适配器在 Persistence 域 |
| 世界规则 | `IWorldRulesView`、`IWorldRulesCommand` | `WorldRulesState` + validated rule commands | 命令验证后一次提交规则快照 | 隐藏秘密种子、难度、矿层和规则兼容 | 掉落/商店/事件只依赖窄视图 | `WorldSession`；规则 Query 靠近消费者 |
| 时间与天气 | `IWorldTimeWeatherView` | `WorldTimeWeatherState` + Clock/Weather System | Clock 只产生边界事实，Weather 只消费时钟与随机源 | 隐藏 Tick/雨/风/节日的相互顺序 | 同一时间视图服务刷怪、事件和 Projection | `WorldSession`；显示适配器在 Presentation |
| 世界进度 | `IWorldProgressView`、`WorldProgressCommand` | `WorldEventProgressState`；Dome 已有 `WorldProgressionState`/显式命令作为部分实现 | `BossDefeated`、`InvasionAdvanced`、`NpcRescued` 命令及 `WorldProgressionTransition` 事实 | 隐藏 bool 群、去重和事件状态机 | 解锁条件可供 NPC、掉落、商店一致读取 | `WorldSession`；事件规则实体归各事件域 |
| 刷怪压力 | `ISpawnPressureView` | `WorldSpawnPressureState` + Spawn System | 写者只在 Spawn System；资格 Query 纯读 | 隐藏 tick 预算与城镇资格计数 | 所有 Spawn 规则共享压力模型 | `WorldSession`；NPC 域承载算法 |
| 存档 | `IWorldSnapshotStore` | `WorldPersistenceAdapter` + versioned `WorldSessionSnapshot` | 适配器是唯一 BinaryReader/Writer 边界 | 隐藏旧版本字段顺序、默认值和临时缓存 | 让模拟不依赖 WorldFile 格式 | Persistence 域，不作为 ECS 组件 |
| 网络 | read-only `WorldSessionProjection`；validated ingress command | packet adapter + Projection | `NetMessage`/`MessageBuffer` 只映射快照或意图 | 隐藏 packet 7/78 和客户端不可信输入 | 网络、UI、日志复用同一投影 | Protocol/Presentation 域，不写权威状态 |

### 4.3 当前实现与目标之间的距离

- `src/WorldSession/WorldSessionComponents.cs` 目前是五个状态定义，未发现对应的运行时 System、命令入口、Persistence Adapter 或网络 Adapter；因此它是组件形状证据，不能作为已迁移行为的证据。
- `dome` 已有可执行的子集：不可变 `WorldProgressionState`、`WorldEventStartCommand`、`WorldProgressionTransition` 和纯 `WorldProgressionQuery`。它证明“显式命令、一次提交、只读投影”可工作，但未覆盖 Version4 的所有 Boss、救援、WorldFile 格式与事件类。
- 当前检查未发现 `src/WorldSession` 与 Dome 这些类型之间的直接连接。接线时必须选定一个权威状态，而不是同时让两个模型写入。

事件专用状态不应全部塞入 `WorldEventProgressComponent`：

- 可跨世界保存的“已击败/已解锁/已救援”放入进度组件。
- 事件当前运行的倒计时、波次、候选实体、临时伤害追踪放到事件规则实体的专用组件。
- 表现历史、公告、音效、客户端倒计时是 `Projection`，不能回写权威状态。

### 4.4 System、Query、Command、Adapter

```text
WorldLoadSystem -> Descriptor/Rules + PreparationState
WorldClockSystem -> WorldTimeWeatherState.Clock -> Weather/EventSchedule
WorldProgressCommandSystem <- BossDefeated / InvasionAdvanced / NpcRescued
WorldProgressCommandSystem -> WorldEventProgressState + WorldRulesState milestones
EventEligibilityQuery <- Rules + Clock + Progress + PlayerCount
EventSchedulerSystem -> Add/Start/End EventRuleEntity commands
PersistenceAdapter <-> typed WorldSnapshot (only authority components)
NetworkProjection <- read-only WorldSessionView + event snapshots

Item/Container/Economy systems --read--> IWorldRulesView/IWorldProgressView
Item/Container/Economy systems --write--> Inventory/Container/Currency commands
```

推荐 Tick 顺序：

1. `WorldLoadBarrierSystem`：未 Ready 时禁止普通模拟。
2. `CommandIngressSystem`：验证网络/管理员/事件命令，形成显式命令。
3. `WorldClockSystem`：推进时间并产生昼夜边界事件。
4. `WorldWeatherSystem`：依据时钟、规则和随机源推进天气。
5. `WorldProgressSystem`：提交 Boss/入侵/救援/生态里程碑；同一 Tick 去重。
6. `EventEligibilityQuery + EventSchedulerSystem`：只读资格，创建/启动/结束事件规则实体。
7. `SpawnAndAiSystem`、`NpcInteractionAndCommerceSystem`、`ItemUseInventorySystem`：消费世界快照。
8. `PersistenceProjection`、`NetworkProjection`、`ClientPresentationProjection`：读取提交后的快照。

必须显式声明：Clock → Weather → Progress → Event eligibility → Spawn/Commerce。不能依赖文件名或组件注册顺序。

## 5. 与“物品、容器与经济事务”系统的接口

目标文档第 12 项列出的 `ItemGameplay`、`WorldObjects`、`InventoryTransferTransactions`、`CommerceTransactionSystem`、`LootResolutionSystem` 应保持独立：

- `CommerceQualificationQuery` 只读取 `IWorldRulesView`/`IWorldProgressView` 判断 hardmode、事件解锁、NPC 服务和商店刷新资格。
- `CommerceTransactionSystem` 以事务方式写入货币余额、库存槽和商店库存；资格失败不得扣款。
- `LootResolutionSystem` 读取 Boss/事件进度和定义目录，产生掉落命令；不得直接把击杀标记写入 NPC 实例。
- `WorldObjects` 的 Chest/Bank/Shop 具有独立生命周期和权限；不把容器内容挂到 WorldSession。
- `InventoryTransferTransactions` 只处理来源槽、目标容器、数量、堆叠和锁定；跨世界规则只通过只读 Query 输入。

这保证“世界进度解锁了某个商店/掉落”与“玩家实际获得物品”是两个可验证的状态转换。

## 6. SS14 可迁移模式与不可照搬部分

### 可迁移模式

- `SharedGameTicker` 把 `RoundId`/`RoundStartTimeSpan` 作为窄只读接口；对应 Version4 的 `IWorldSessionView`。
- `GameTicker.RoundFlow` 把开始、结束、重启、暂停、地图加载和清理拆成明确阶段；对应 `WorldLoadSystem` 与 `WorldSessionLifecycleSystem`。
- `GameRuleComponent + ActiveGameRuleComponent + EndedGameRuleComponent` 用实体标签表达规则生命周期，避免一个全局列表同时承载配置、运行态和终止态。
- `GameTicker.GameRule` 的 Added → (Delayed) → Active → Ended 事件及 `AllPreviousGameRules` 历史，适合映射 Terraria 事件的调度、去重和审计历史。
- `BasicStationEventSchedulerComponent` 为每个调度器实体保存独立计时器；可用于拆出天气、入侵、月事件的调度状态。
- `EventManagerSystem.CanRun` 将玩家数、当前时间、最少间隔、最大次数和回合结束资格集中为纯资格判断；对应 `WorldEventEligibilityQuery`。
- `GlobalTimeManagerComponent`/`ClockComponent` 分离全球时间权威与时钟显示；对应 Version4 的 Clock 与 Presentation 分离。

### 不可照搬部分

- SS14 的 `RoundRestartCleanupEvent` 会清空回合实体和规则；Terraria 的世界进度必须跨服务器重启/世界保存保留。
- SS14 的 `GameRule` 多为回合内事件，Terraria `downedBoss`/`savedNPC` 是世界存档事实，不能仅作为短命规则实体。
- SS14 地图原型/MapPool 选择不能替代 Terraria 的 Tile/WorldFile 二进制格式、种子和生态扩散。
- SS14 的 `IGameTiming.CurTime` 是服务器回合时钟；Terraria 的 `Main.time/dayTime` 有昼夜循环、天气和月相语义，必须保留独立领域模型。

## 7. 兼容策略与不拆分项

### 7.1 兼容策略

1. 先建立 `WorldSession` 实体和只读门面，将旧 `Main.*`/`NPC.downed*` 入口改成单向 Adapter。
2. `WorldFileAdapter` 负责旧版本字段顺序、默认值和版本迁移；组件只接受 typed snapshot，不让 BinaryReader/Writer 渗透核心。
3. 迁移期间禁止新旧字段双写：旧字段可由组件投影生成，权威写入只走 `WorldProgressCommandSystem` 等 System。
4. 网络包和存档 DTO 使用 `WorldSessionSnapshot`/`EventProgressSnapshot` Projection；客户端发送的“已完成/已扣款”只作为意图或诊断，服务器重新从权威状态计算。
5. 对未知事件 ID、非法进度位、版本不兼容、重复击杀命令和槽位冲突显式返回错误，不静默吞异常。

### 7.2 暂不拆分/合并理由

- `WorldDescriptorState` 与 `WorldRulesState` 分开：描述字段在生成/加载时写入，规则字段在玩法命令和种子初始化时写入，生命周期不同。
- `WorldTimeWeatherState` 内部保留 Clock/Weather 两个责任区，而非再增加一级组件：天气读时钟但有自己的随机过程和暂停/冻结能力，实际接线时由两个 System 形成单向顺序。
- Boss/救援/入侵进度不按每个 Boss 创建数十个实体：这些是同一世界聚合内的可版本化标记，使用结构化位图/记录比大量实体关系更稳定。
- `WorldEventProgressComponent` 不包含事件临时计时器：临时计时器与事件实体生命周期一致，放入规则组件可避免存档污染。
- `WorldGen` 的背景样式、tileCounts、SceneMetrics 不作为第一批权威组件：它们是派生/表现缓存，待失效条件和性能证据闭合后再决定是否缓存。

## 10. 最终拆分建议

推荐的最小可交付切片是：

```text
WorldSessionEntity
  ├─ WorldDescriptorState
  │    └─ identity/bounds/seed/load lifecycle
  ├─ WorldRulesState
  │    └─ difficulty/secret seed/evil/ore/milestones
  ├─ WorldTimeWeatherState
  │    └─ clock/weather/moon/seasonal durable state
  ├─ WorldEventProgressState
  │    └─ boss/rescue/invasion/DD2 durable progress + pending events
  └─ WorldSpawnPressureState
       └─ spawn cadence/town checks/event budget

Systems:
  WorldLoadSystem -> WorldClockSystem -> WorldWeatherSystem
  -> WorldProgressSystem -> EventSchedulerSystem (event-rule entities)
  -> Spawn/Ai + Item/Commerce systems
  -> Persistence/Network/Presentation projections
```

这套边界满足文档要求的“世界会话/世界存储/内容目录分层”、保留 Version4 的存档与事件语义，并吸收 SS14 已验证的规则实体、生命周期事件、窄只读视图和独立调度器模式。它仍是待实现设计；本轮正式 serial verifier 因遗留 MSBuild 进程未完成，且 focused verifier、存档夹具尚缺，不能把它标记为迁移完成。
