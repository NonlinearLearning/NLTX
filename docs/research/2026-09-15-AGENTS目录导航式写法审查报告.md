## 2. 结论先行

本仓库需要的不是“更完整的 `AGENTS.md`”，而是“更短、更明确的入口文件”。根级 `AGENTS.md` 应该承担四件事：

1. 说明当前目录树的职责和边界。
2. 根据任务类型把代理路由到唯一权威文档、脚本或目录级 `AGENTS.md`。
3. 说明作用域、继承和冲突处理方式。
4. 保留少量不能从目录或配置直接推断出的仓库约定。

具体命令、参数、进程检查、代码风格条款、ECS 文件组织规则和副作用规则应继续留在它们各自的权威文件中。`AGENTS.md` 只写“何时读哪个文件”，不再写“被指向的文件具体规定了什么”。

对当前文件的核心判断是：现有内容的技术方向大多有价值，但信息层级混在了一起。`ECS File Organization`、`C# Code`、`Side-Effect Isolation`、`Build Environment` 和 `Dotnet Build Concurrency Contract` 都包含可执行的规范正文，因而不属于纯导航式根入口。它们应压缩为任务触发器和链接；规范正文保留在 [`Context/架构设计/`](../../Context/架构设计/)、[`Context/约束/`](../../Context/约束/) 和 [`Build/Tools/`](../../Build/Tools/) 中。

## 3. 什么是目录导航式 AGENTS.md

### 3.1 应该保留的内容

导航式文件的每一段都应回答“遇到什么任务，下一步去哪里”。适合保留以下信息：

| 内容 | 作用 | 推荐写法 |
| --- | --- | --- |
| 作用域 | 说明文件覆盖哪些目录 | “本文件覆盖仓库根目录；更深层文件只补充局部信息。” |
| 仓库地图 | 让代理先定位领域、源码、测试、脚本和文档 | `路径 -> 用途 -> 首先阅读的入口` |
| 权威索引 | 让每类规则只有一个事实源 | “修改 ECS 文件时先读 `Context/架构设计/...`。” |
| 任务路由 | 把任务分支连接到资料 | “修改 C# 时读 `Context/约束/...`；构建时进入 `Build/Tools/...`。” |
| 局部入口 | 说明哪些子目录有独立上下文 | “进入 `apps/studio/` 后继续读取其 `AGENTS.md`。” |
| 维护规则 | 防止入口链接失效或与正文分叉 | “移动权威文件时同步更新本索引。” |

### 3.2 不应该放在根入口的内容

下面这些内容即使正确，也应该下沉到规范、脚本、配置或 CI：

- 完整命令块、参数组合、PowerShell 变量和进程检查脚本。
- C# 命名、缩进、控制流等完整风格条款。
- ECS 文件移动、组件命名、副作用隔离的具体判定规则。
- 构建并发、锁、重试、产物目录和失败处理的详细操作合同。
- 多个例外情形、历史背景和长篇实现说明。

根入口可以写“构建或测试任务进入串行包装器”，但不应复制包装器的参数协议。根入口可以写“副作用隔离规则见某文件”，但不应再解释 I/O、时钟、随机性和重试的具体设计要求。

### 3.3 一个可操作的判断测试

逐段询问：

> 删除这一段后，代理是否仍然能通过链接找到唯一权威规则？

如果答案是“能”，这段通常是重复正文，应下沉；如果答案是“不能”，这段可能是必要的导航或作用域信息。另一个测试是：一条规则变化时是否需要同时修改 `AGENTS.md` 和另一份规范？如果需要，说明存在重复事实源。

### 5.1 样本归纳

从样本中可以抽出三种可复用形态：

1. **纯指针型**：VS Code 根文件。它把代理必须知道的下一入口说清楚，细节完全外置。
2. **目录地图型**：Supabase、Next.js、Strapi、Cline。它们先回答“哪个目录负责什么”，再指向局部文件或工具说明。这是大型 monorepo 最适合借鉴的形态。
3. **局部边界型**：OpenAI Codex 的 `bottom_pane/AGENTS.md`。它只记录当前目录独有的同步对象和局部验证入口，适合本仓库未来的 `src/某领域/`、`Test/某验证器/` 等稳定边界。

Node.js、Rust、Kubernetes 和 ESLint 的文件则证明了另一件事：文件名叫 `AGENTS.md` 并不自动意味着它是导航文件。它们是有效的 agent 指导文档，但把政策、命令和硬约束直接写在入口中；这正是当前仓库应该有意避免的混合方式。

### 6.2 用户给出的副作用段落应如何收缩

当前示例：

```markdown
## Side-Effect Isolation

- For imperative C#, ECS systems, background tasks, and protocol adapters, use the draft rules in
  [Context/约束/非函数式编码副作用隔离规范.md](../../Context/约束/非函数式编码副作用隔离规范.md).
- Keep business rules as deterministic calculations where practical; isolate I/O, clocks,
  randomness, logging, persistence, messaging, and UI effects behind explicit ports and adapters.
- Keep effect ordering, ownership, failure, and retry behavior visible and testable.
```

导航式版本只需要表达触发条件和目标位置：

```markdown
## Rule Routing

- 修改命令式 C#、ECS 系统、后台任务或协议适配器时，先读
  [`Context/约束/非函数式编码副作用隔离规范.md`](../../Context/约束/非函数式编码副作用隔离规范.md)。
```

确定性计算、端口与适配器、效果顺序和重试可测试性都属于被指向文档的正文；它们不应在根入口再出现一遍。

### 6.3 构建段落应如何收缩

当前 `Required command shape` 的 PowerShell 示例、`Get-CimInstance` 进程筛选、`-m:1` 和多个 `-p:` 参数都是可执行操作合同，不是目录导航。导航式根文件应只写：

```markdown
## Rule Routing

- 编译、测试、运行或发布任务：先进入
  [`Build/Tools/Invoke-SerialDotnet.ps1`](../../Build/Tools/Invoke-SerialDotnet.ps1)，并读取其相邻构建说明。
- 构建产物和验证记录：查看 `Build/bin/`、`Build/obj/`、`Build/generated/`、`Build/packages/` 的归属说明。
```

精确参数协议应该由包装器的参数定义、构建文档或自动化检查维护，避免入口示例和脚本接口分叉。

## 7. 推荐的根级模板

下面的模板故意不写具体命令和规范正文，只提供路由骨架：

```markdown
# Repository Agent Index

This file is the repository navigation layer. Canonical rules live in the linked documents,
scripts, and directory-scoped agent files.

## Scope

- This file covers the repository root.
- A deeper `AGENTS.md` adds facts for its directory and its descendants.
- Follow the nearest applicable directory entry after reading the root map.

## Start Here

- Current repository context: `Context/progress.md`
- Documentation lifecycle: `dome/dome1/docs/flowstate/README.md`
- Plans, decisions, research, and migrations: `docs/`

## Repository Map

| Path | Responsibility | Read first |
| --- | --- | --- |
| `src/` | Main domain and ECS source tree | Affected project and domain directory |
| `src2/` | Secondary domain or migration tree | Affected project and local guide |
| `Test/` | Verification projects | Target verifier project |
| `Build/Tools/` | Build and verification entry points | Selected script and its help/documentation |
| `docs/` | Plans, decisions, research, and process records | Topic-specific index |
| `Context/架构设计/` | ECS organization and naming authorities | Relevant architecture constraint |
| `Context/约束/` | C# and side-effect authorities | Relevant coding constraint |

## Rule Routing

- ECS file or component change: read the applicable documents under `Context/架构设计/`.
- C# change: read the applicable document under `Context/约束/`.
- Command-style system, background task, or adapter change: read the side-effect authority.
- Compile-capable work: enter through `Build/Tools/`.
- Documentation or planning work: start at `Context/progress.md` and the applicable `docs/` index.

## Local Instructions

- Read a deeper `AGENTS.md` when the target path has one.
- Keep directory-scoped files limited to facts and routes unique to that directory.
- Keep canonical rules in one source and update this index when an authority moves.
```

该模板的关键不是固定这些目录名，而是固定信息形态：`路径 -> 责任 -> 下一入口`，以及`任务触发器 -> 唯一权威源`。

## 8. 对本仓库的实施建议

1. 将根级 `AGENTS.md` 改成“作用域 + 仓库地图 + 权威索引 + 任务路由”四段式入口。
2. 删除根文件中的完整命令块、进程筛选脚本、参数组合和详细 C# / ECS / 副作用条款；保留指向权威文件的短句。
3. 对 `src/`、`src2/`、`Test/`、`dome/`、`Build/Tools/` 和 `docs/` 建立最小目录地图。地图描述职责，不描述运行时执行顺序。
4. 只有在某个子目录拥有稳定边界、独立验证方式或独立迁移单元时，才新增目录级 `AGENTS.md`；内容采用 OpenAI Codex `bottom_pane` 样本的局部写法。
5. 把所有相对链接当作入口契约检查。当前 [`Context/progress.md`](../../Context/progress.md) 仍引用不存在的 `docs/flowstate/README.md`，实际 Flowstate 入口是 [`dome/dome1/docs/flowstate/README.md`](../../dome/dome1/docs/flowstate/README.md)，应在后续文档维护中统一。
6. 将“链接目标存在、入口没有复制规范正文、目录地图与实际目录一致”作为文档变更验收条件；这类文档变更不需要运行无关的 .NET 构建。

## 9. 研究判断

本次外部样本支持以下判断：

- 最稳定的根级写法是 VS Code 式的短指针：先告诉代理详细事实在哪里。
- 大型 monorepo 最有用的增量是 Supabase 式目录地图：目录职责和嵌套入口同时出现。
- 目录级文件最适合记录 OpenAI Codex `bottom_pane` 式的局部边界和局部验证，而不是重新声明根规则。
- 高星项目中的长篇 `AGENTS.md` 可以是有效文档，但不应被误认为“导航-only”范式。当前仓库的目标应明确采用前两类，避免复制后四类混合正文。
