## 一、当前迁移项目是什么

仓库已经不是一个简单的“改名或搬文件”项目，而是在建立一套可长期演进的服务器内核边界：

- PRD 将 `EntityUuid` 定义为服务器权威实体实例的运行时身份根，并把 `whoAmI`、Projectile identity、`PlayerHandle`、`NpcHandle`、`ReplicationId`、账户 UUID 和持久化 ID 限制为不同作用域的 typed projection。
- ADR 已接受 Registry/Adapter 分层，明确 Registry 只管理身份关系、冲突和生命周期，不承载 Player/NPC/Projectile 领域状态。
- 迁移账本已覆盖 506 个源成员、506 条 decision、3,210 条证据和 64 个 work item；76 条有明确 move/merge/split 目标但仍是 migrated，430 条 deferred，verified 为 0。
- 当前仓库有大量 focused verifier、领域组件和分区报告，说明你已经在建立“可审计迁移”流程，而不是凭聊天记录推进。
- `Context/progress.md` 明确当前没有激活的迁移批次，意味着下一步必须从账本和计划恢复一个小而完整的工作切片。

这套设计的风险在于：账本通过不等于运行时等价。当前最重要的未知量是四类实体是否在真实 tick、连接、复制、重生、断线重连和恢复路径上保持原有行为。

## 三、能力画像

### 已形成的优势

- **复杂系统分解**：能按领域拆分 World、Player、NPC、Projectile、Physics、Liquid、Persistence 等边界，并维护文件组织约束。
- **迁移治理**：有 PRD、ADR、计划、账本、审计、focused verifier 和恢复包，工程纪律明显强于普通原型项目。
- **跨语言和跨层能力**：C/C++、C#、Python、FreeRTOS、驱动和工具链经验使你能理解从字节到领域模型的整条链路。
- **测试与证据意识**：已有协议、世界生成、战斗、组件、输入同步等验证项目；这为建立服务器回归矩阵提供基础。
- **适配器思维**：当前身份根/typed projection 设计正确地避免了把协议槽位、账户身份和运行时实体混成一个主键。

### 需要警惕的工作倾向

- **结构先行，行为滞后**：目录、组件、账本和静态扫描进展很快，但 verified 仍为 0；容易把“映射完整”误判成“运行时迁移完成”。
- **工具和文档投入可能超过垂直闭环**：分析工具很强，但需要固定比例时间做可运行的 Spawn → Tick → Replicate → Disconnect → Restore 闭环。
- **身份抽象存在过度设计风险**：`EntityUuid`、Handle、Protocol identity、ReplicationId、AccountUuid、PersistentEntityId 各自正确，但必须用少量真实流程证明每个边界，否则会增加调用复杂度。
- **游戏语义经验不足**：代码能力足以实现框架，但伤害判定、客户端输入不可信、tick 顺序、快照差异、重连和作弊面需要专门补课。

## 四、知识缺口与学习目标

### 1. 权威模拟与 tick 模型（最高优先级）

需要掌握：固定 tick 与帧率解耦、输入采样、系统执行顺序、生成/销毁提交点、时间漂移、暂停和慢 tick、确定性边界。目标是能画出 Player/NPC/Projectile 一次 tick 的完整时序，并说明每个字段何时可读、何时可写、何时提交。

建议产出：一个最小服务器模拟器，支持 2 个客户端输入、碰撞、生成 Projectile、固定 tick、迟到输入和可重放日志。

### 2. 网络复制与信任边界

需要掌握：客户端输入命令与服务器状态的区别、snapshot/delta、可靠与不可靠消息、序列号、ack、重传、丢包/乱序、重连和全量重同步、客户端预测与服务器校正。必须能回答“哪些数据服务器永远不会发给客户端”“哪些字段客户端可以请求但不能指定”。

建议产出：保持现有 Terraria 包布局的 Adapter 测试，覆盖槽位复用、旧包、未知实体、重复包、乱序包和重同步。

### 3. ECS 与性能

需要掌握：组件布局、稀疏集合/ archetype、查询成本、缓存局部性、结构变化、对象池、分配、锁竞争、跨线程消息和 tick budget。不要只看平均吞吐，还要看 P99 tick 时长、最大实体数、复制字节数和 GC 暂停。

建议产出：基准表：实体数 × Projectile 数 × 玩家数，对比全扫描、typed index、Registry 查询的 CPU、分配和尾延迟。

### 4. 持久化与恢复

需要掌握：世界存档与玩家存档边界、版本迁移、幂等写入、崩溃一致性、检查点、恢复引用修复、临时实体与持久化实体的差别。`EntityUuid` 不能成为跨重启主键，这一点设计上已明确，但需要真实恢复流程验证。

建议产出：一次故障注入测试：在写入中途终止，恢复后创建新运行时 UUID，并对无法解析的引用进入显式失败路径。

### 5. 服务器运维与安全

需要掌握：连接认证、权限、速率限制、审计日志、指标、结构化日志、追踪、优雅停机、健康检查、配置热更新边界和故障隔离。游戏服务器的安全重点是客户端不可信、资源耗尽和状态污染，而不仅是传统 Web 身份认证。

### 6. Terraria 领域语义

需要建立 Player/NPC/Projectile/World/TileEntity/Item 的生命周期词典：spawn、despawn、重生、所有者、伤害来源、AI、碰撞、掉落、世界保存、网络可见性。先掌握首批四类实体，再扩展 WorldItem、Chest 等对象。

## 五、建议的 90 天补齐路线

### 第 1–2 周：建立服务器心智模型

阅读当前 PRD、ADR、账本和 Version4 对应实现；画出一张 tick 时序图和一张身份/协议/账户/持久化边界图。实现最小单线程模拟器，不接真实网络。

### 第 3–4 周：做一条完整垂直切片

只选择 Player + 一个 Projectile：权威 Spawn、输入、移动、碰撞、伤害、复制、销毁、重连。每一步都要有 focused verifier 和可重放事件日志，目标是产生第一个 `verified` 而不是继续扩大组件目录。

### 第 5–8 周：补网络和恢复

加入丢包、乱序、重复、迟到输入、槽位复用、全量重同步和断线重连；加入持久化恢复与引用修复。记录带宽、P99 tick、分配和错误分类。

### 第 9–12 周：扩大实体范围并做回归

将同一模式扩展到 NPC，再到玩家/NPC Projectile；运行协议兼容、生命周期、Registry 冲突、预测隔离和迁移 guard verifier。只有行为证据闭合后，才删除旧核心写路径。

## 六、每周应检查的指标

- 已迁移成员中 `verified` 数量及其对应端到端路径；
- Spawn、Tick、复制、销毁、重连、恢复各阶段的覆盖率；
- P50/P95/P99 tick 时长、GC 分配、最大实体数和复制字节数；

- 旧身份字段在核心 Simulation 中的读写数量；
- 通过重放得到的状态哈希是否稳定；
- 发生故障时是否能从日志恢复实体身份和事件因果链。

### 10.2 重新校准后的结论

你不是“完全没有服务器基础”的初学者。你已经具备 TCP/帧处理、协议状态机、并发队列、静态分析、迁移治理、故障诊断和验证器建设能力；真正欠缺的是**多人游戏服务器的运行时语义**：在每个 tick 中，服务器如何把不可信输入变成权威状态，如何只向每个客户端复制它应看到的状态，如何处理迟到/重复/断线输入，以及如何在崩溃后恢复可继续运行的世界。

因此，当前最准确的判断不是“代码量不够”，而是：**结构迁移推进很快，端到端运行证据尚未闭合。** 现有 `Context/progress.md` 和旧报告中的 `verified = 0` 仍应作为迁移成熟度的重要信号；有组件、Command、System 或 focused verifier，不等于这些对象已经接入主循环并保持了旧运行时行为。

### 10.4 既有项目证明的能力与暴露的问题

`D:\ProjectItem\SourceCode` 中的旧项目进一步确认了你的优势，但也显示了迁移时最容易复发的风险：

- `Net/Networking/NetworkLayer/Network/NetworkServer.cs:16-76` 已有 TCP server、session map、收发队列、连接事件、粘包拆包和批量发送；这证明你能实现传输层。但接收队列在该实现中没有和当前 Dome 一样清晰的容量/拒绝策略，`SendAsync` 的失败和关闭语义也没有形成完整的可审计流程。
- `ProtocolHandshakeProcess.cs:49-92` 已有版本、密码、握手阶段和 socket 控制移交概念；注释同时明确写出同步阶段的阻塞发送、错误断开和 socket 交接尚未完成。这是很好的自我识别证据，也说明旧的握手状态机不能直接视为生产级认证和会话生命周期。
- `Networking/Verification/Verification.md:3-9, 13-69` 体现了将旧 `MessageBuffer` 与新 PacketHandler 做收发一致性对照的意识，但后续多次运行出现 `MessageBuffer.GetData` 空引用失败。你已经掌握“用差分验证迁移”的方法，下一步要补的是稳定的 fixture、生命周期初始化和失败分类。
- `Terraria/TShock/PlayerDeath/Plugin.cs:35-45, 120-226` 使用事件、队列、Timer、后台 Task 和锁；`PlayerDeath` 状态主要按名称和槽位维护。它适合说明你熟悉异步业务插件，但也暴露出重连身份、槽位复用、时序和关闭竞态需要在服务器核心中单独建模。
- `Terraria/TShock/MapViewShare/Plugin.cs:45-46, 155-190, 245-280` 使用并发队列、对象池和坐标聚合，同时在 `155-157` 存在嵌套遍历。它说明你有性能意识，但游戏服务器性能必须以实体规模、tick 尾延迟、复制字节和分配量实测，不能仅凭引入对象池或组件化推断已经足够快。
- `Net/NL`、`NL-performance-fact-propagation` 和 `TerrariaTools` 显示出静态分析、调用图、规则管线、差分验证、性能测量和 fail-closed 思维。这是迁移治理的强项，但这些工具能力需要转化为“某个玩家从连接到重连的行为证据”，否则仍停留在结构正确性层。

### 10.6 最优先的学习顺序

**P0：权威 Tick 和输入语义。** 先掌握固定时间步、输入采样、阶段/屏障、结构变化提交、超载处理和确定性边界。重点不是背某个引擎 API，而是能回答：一个客户端在 tick `T` 提交的移动、开火、Tile 操作分别何时进入队列、何时验证、何时改变权威状态、何时可被复制。

**P0：复制与重同步。** 学习 snapshot、delta、revision、序列号、ack、丢包、重复、乱序、迟到输入、兴趣区域和全量重同步。Unreal 的 Replication 资料适合建立问题地图，Roblox 资料适合校准信任边界，二者都不能替代本地 Terraria 包行为核对。

**P0：实体生命周期和身份。** 以 Player + Projectile 为第一组实体，完整记录连接、分配槽位、spawn、移动、命中、销毁、重连、重生和恢复。尤其要验证 `whoAmI`/协议槽位、`EntityUuid`、`ReplicationId`、AccountUuid 和持久化身份在槽位复用后不会指向错误实体。

**P1：持久化和故障恢复。** 学习检查点、临时文件、原子替换、备份选择、版本迁移、幂等和引用修复；把“文件写成功”升级为“进程在任意写入点崩溃后，服务器能明确恢复或安全拒绝启动”。

**P1：性能和可观测性。** 学习 tick P50/P95/P99、GC、分配、锁竞争、队列深度、复制字节、实体容量和慢客户端隔离。`dotnet-trace`、`dotnet-counters` 与结构化指标应服务于决策，而不是成为额外的工具目录。

**P1：安全与运维。** 学习认证、权限、速率限制、资源耗尽、包大小限制、恶意序列化、审计、优雅停机和健康检查。游戏服务器的核心安全问题是客户端不可信、状态污染和资源耗尽，不只是密码握手。

### 10.7 推荐的第一条垂直切片

不要先继续横向增加实体目录。选择 **一个 Player、一个 Projectile、两个客户端**，完成以下链路：

```text
连接/握手
  -> 分配会话与玩家身份
  -> 客户端输入命令（含 tick/sequence）
  -> 服务器校验并在固定 Tick 应用
  -> 服务器生成 Projectile
  -> 权威移动、碰撞、伤害、销毁
  -> 按可见性生成 snapshot/delta
  -> 丢包/重复/乱序/迟到输入
  -> 断线重连与全量恢复
  -> 世界/玩家持久化与崩溃恢复
```

这条切片的最低验收标准是：

- 客户端不能指定最终位置、伤害、Projectile 所有者或任意实体身份；
- 1000 个固定 tick 的同一输入回放能得到稳定状态哈希，或能明确记录非确定性来源；
- 重复、乱序和迟到输入不会重复造成伤害、掉落或结构变化；
- 槽位释放后重新分配不会让旧包绑定到新玩家；
- 断线重连能获得完整且版本正确的权威状态；
- 模拟超载时队列有上限、行为有记录、服务器不会无界积压；
- 在存档写入不同阶段故障后，启动程序能选择主文件、备份或显式拒绝，并留下可审计原因；
- 至少记录 tick P50/P95/P99、GC 分配、入出站队列深度、复制字节和拒绝原因。

### 10.8 90 天路线的调整版

**第 1-2 周：心智模型。** 画出一张 tick 时序图、一张身份边界图和一张连接状态图；实现不接真实网络的双客户端最小模拟器，包含输入序号、固定 tick、Projectile、命中和事件回放。
