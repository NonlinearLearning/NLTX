# Version4 与 SS14 参考模型的 ECS 组件拆分合理性报告

## 1. 报告范围

本报告只讨论组件拆分是否合理。

对照材料：

- Terraria 字段来源：`D:\TRbackup\Version4`
- ECS 粒度参考：`C:\Users\shan\Downloads\ECS\space-station-14-master`
- NLTX 既有共享组件：`D:\TRbackup\NLTX\src\Share\Entity\Components`

判定标准只有三项：

1. 组件内字段是否由同一类规则共同读取和更新。
2. 拆开后是否减少无关系统携带的状态。
3. 拆开后是否产生比原设计更严重的跨组件不变量。

## 2. 已有组件不重复拆分

以下组件已经位于 [src/Share/Entity/Components](D:/TRbackup/NLTX/src/Share/Entity/Components)，本报告只把它们作为已确认的拆分基线：

| 组件 | 对应 Version4 字段 | 拆分判断 |
| --- | --- | --- |
| `LocationComponent` | `Entity.position` | 合理：位置是独立的空间状态 |
| `VelocityComponent` | `Entity.velocity` | 合理：速度是独立的运动状态 |
| `ColliderComponent` | `Entity.width`、`height` | 合理：几何边界与碰撞结果分开 |
| `DirectionComponent` | `Entity.direction` 的水平分量 | 合理：只表达稳定的基础朝向 |
| `LiquidComponent` | `Entity.wet` 等接触状态 | 合理：实体接触状态独立于其他空间字段 |
| `EntityIdentityComponent` | 实体实例身份 | 合理：实体自身身份独立于关系目标 |

这些既有组件不应再次包装为 `BaseEntityComponent`、`SpatialComponent` 或其他聚合组件；聚合会重新引入被拆开的无关状态。

## 4. 已确认合理的组件拆分

### 4.1 `HealthComponent` 与 `MobStateComponent`

**拆分合理。**

- `HealthComponent` 表达当前生命和最大生命，是连续数值状态。
- `MobStateComponent` 表达存活、濒死、死亡等离散阶段。
- 伤害、治疗和生命显示只需要生命数值；死亡、复活和失能规则只需要阶段状态。
- 合并会使只处理生命数值的代码携带死亡阶段，也会让生命变化和阶段变化难以区分。

### 4.2 `HealthComponent` 与 `DefenseComponent`

**拆分合理。**

- Health 是受击后的结果状态。
- Defense 是伤害计算的输入状态。
- 装备、效果或 NPC 定义可以改变 Defense，但不应因此重置 Current Health。
- 治疗和复活只需要 Health；防御重算只需要 Defense。

### 4.3 `DefenseComponent` 与 `ImmunityComponent`

**拆分合理。**

- Defense 表达伤害进入后如何减免。
- Immunity 表达伤害是否允许进入结算。
- “拒绝伤害”和“降低伤害”是不同结果，使用者和更新原因不同。

### 4.4 `HealthComponent` 与 Mana/Stamina 等资源组件

**拆分合理。**

- Health 归零影响实体生存阶段。
- Mana、Stamina、能量等资源归零通常只影响技能或行动资格。
- 资源虽然也有当前值和最大值，但单位、恢复原因和耗尽后果不同。
- 合并成通用资源组件会引入大量资源类型分支，削弱组件局部性。

### 4.5 `ProjectileLifetimeComponent` 与 `ProjectileBehaviorComponent`

**拆分合理。**

- Lifetime 表达投射物还能存在多久以及何时结束。
- Behavior 表达 AI 状态、额外更新和运行期间行为。
- 同一行为可以使用不同寿命；同一寿命也可以承载不同 AI。
- 合并会把高频行为状态与生命周期状态绑定在一起。

### 4.6 `ProjectileDefinitionComponent` 与 `ProjectileBehaviorComponent`

**拆分合理。**

- Definition 是生成时确定的能力配置。
- Behavior 是实例运行期间变化的状态。
- 多个实例可以共享相同定义而拥有不同的行为进度。
- 静态配置不应随每 tick 的行为状态一起变化。

### 4.7 `ProjectileOwnerComponent` 与 `ProjectileDamageComponent`

**拆分合理。**

- Owner 表达生成归属和关系。
- Damage 表达命中时提供的攻击能力。
- 所有者关系用于归因和友伤判断；伤害能力用于命中结算。
- 一个字段变化不应要求另一个字段同时存在或更新。

### 4.8 `ProjectileDamageComponent` 与 `HealthComponent`

**拆分合理，而且必须分开。**

- Projectile Damage 是攻击输出。
- Health 是目标的受击状态。
- 投射物被销毁或穿透，不通过 Health 表达其存在状态。
- 合并会把“造成多少伤害”误解成“自身还有多少生命”。

### 4.9 `InputIntentComponent` 与 `VelocityComponent`

**拆分合理。**

- InputIntent 表达控制者想做什么。
- Velocity 表达移动规则处理后的运动结果。
- 输入可能被碰撞、重力、液体或失能状态抑制；速度也可以由 AI、击退或环境力改变。
- 合并会让输入层直接拥有物理结果，无法表达意图与结果之间的差异。

### 4.10 `InventoryComponent` 与 `HandsComponent`

**拆分合理。**

- Inventory 表达库存、装备槽和物品组织。
- Hands 表达活动手、当前持有物和手部操作关系。
- 储物对象可以有容纳能力但没有手部；角色也可能有手部关系而库存布局不同。
- 合并会让库存查询携带高频手部状态，让手部操作携带完整库存结构。

### 4.11 `ItemDefinitionComponent` 与 `StackableItemComponent`

**拆分合理。**

- ItemDefinition 表达物品类型和静态能力。
- Stackable 表达实例数量和堆叠上限。
- 使用、消耗、拆分和合并只改变数量，不应重写整套物品定义。
- 不可堆叠装备仍可拥有定义组件，但不需要可变堆叠状态。

### 4.12 `EquipmentComponent` 与 `WeaponComponent`

**拆分合理。**

- Equipment 表达穿戴关系和占用槽位。
- Weapon 表达攻击方式、伤害、弹药或使用能力。
- 护甲和装饰物可以没有武器能力；武器也不一定占用传统装备槽。
- 合并会让装备更新与攻击冷却、弹药和投射物生成互相耦合。

### 4.13 `ContainerComponent` 与 `InventoryComponent`

**拆分合理。**

- Container 表达实体能否容纳其他实体。
- Inventory 表达角色如何组织和使用自己的物品槽位。
- 箱子、机器和掉落容器可以有 Container，但没有角色 Inventory。
- 合并会把角色专属槽位语义扩散到所有普通容器。

### 4.14 `TargetingComponent` 与 `NpcAiStateComponent`

**拆分合理。**

- Targeting 表达当前目标关系。
- NpcAiState 表达行为阶段、行为计时和 AI 内部状态。
- 目标可以在同一行为阶段内切换；AI 也可以在没有目标时继续运行。
- 合并会让目标失效和行为重置互相污染。

### 4.15 `TargetingComponent` 与 `ProjectileOwnerComponent`

**拆分合理。**

- Targeting 是动态选择结果。
- ProjectileOwner 通常在生成时确定，是归属关系。
- NPC 可以有目标但没有 ProjectileOwner；投射物有所有者但不一定有当前目标。

### 4.16 `EntityIdentityComponent` 与 `EntityReference`

**拆分合理。**

- Identity 表达实体自身是谁。
- EntityReference 表达某个关系字段指向谁。
- 实体身份通常稳定；目标、所有者或容器关系可以变化。
- 二者都使用 UUID 词汇，不代表它们具有相同所有权或生命周期。

### 4.17 `StatusEffectsComponent` 与 `TimedStatusEffect`

**拆分合理。**

- `TimedStatusEffect` 是单条效果记录。
- `StatusEffectsComponent` 是实体当前效果集合。
- 单条效果可以被替换或到期；集合负责保存多条效果的整体状态。
- 合并会让单条记录承担集合职责，或让集合结构重复嵌入每条记录。

### 4.18 通用 `DirectionComponent` 与专用方向状态

**拆分合理。**

- 通用方向只表达稳定的基础水平朝向。
- Projectile 还需要发射角、轨迹方向或精灵方向；NPC 可能需要垂直方向和行为转向；Player 可能需要输入朝向和瞄准方向。
- 这些值的更新原因不同，不能因为都使用整数或角度就合并。

### 4.19 `ColliderComponent` 与碰撞结果/碰撞策略

**拆分合理。**

- Collider 表达稳定几何边界。
- 碰撞结果表达本次检测发生了什么。
- 碰撞策略表达实体如何处理接触、阻挡、穿透或忽略 Tile。
- 几何边界、瞬时结果和领域策略的生命周期不同。

### 4.20 三类实体生命周期组件保持分开

**拆分合理。**

- Player 生命周期包含死亡、复活和会话相关状态。
- NPC 生命周期包含自然消失、击杀和生成/段节相关状态。
- Projectile 生命周期包含寿命耗尽、命中销毁、穿透耗尽和结束保留状态。
- 它们都可能出现“活动”和“剩余时间”，但终止原因与恢复路径不同，不能合并。

### 4.21 实体液体接触与世界格子液体状态

**拆分合理。**

- 实体液体状态表达实体正在接触或受到液体影响。
- 世界格子液体状态表达 Tile 储存的液体和流动状态。
- 一个实体可同时接触多个格子，一个格子也可影响多个实体；二者不是同一份状态。

### 4.22 网络复制状态与领域状态

**拆分合理。**

- 领域组件表达游戏规则中的权威状态。
- 网络状态表达复制游标、脏标记或发送侧状态。
- 网络发送失败或视野变化不应改变生命、位置、目标或寿命。

## 5. 不建议合并的组件组合

以下组合即使在旧类中相邻、字段名称相似，也不应合并：

| 不建议合并 | 原因 |
| --- | --- |
| Health + ProjectileDamage | 目标生命与攻击输出语义相反 |
| Health + MobState | 连续数值与离散阶段变更不同 |
| Health + Mana/Stamina | 生存资源与行动资源单位及后果不同 |
| Defense + Immunity | 伤害减免与伤害资格不同 |
| ProjectileLifetime + ProjectileBehavior | 存在期限与运行行为不同 |
| ProjectileOwner + Targeting | 固定归属与动态目标不同 |
| InputIntent + Velocity | 控制意图与物理结果不同 |
| Inventory + Hands | 库存组织与当前操作关系不同 |
| ItemDefinition + Stackable | 静态能力与实例数量不同 |
| Equipment + Weapon | 穿戴关系与攻击能力不同 |
| EntityIdentity + EntityReference | 自身身份与关系目标不同 |
| Entity Liquid + Tile Liquid | 实体接触与世界储存不同 |
| Domain State + Replication State | 游戏权威与传输状态不同 |
| Simulation State + Render/History State | 服务器规则与客户端表现不同 |

## 6. 表现组件排除

`RenderStateComponent` 和 `PresentationHistoryComponent` 不属于服务器共享组件，本报告不将它们列为可加入 `src/Share` 的候选。`rotation`、`gfxOffY`、`oldPos`、`oldRot` 等字段即使在 `Version4` 的多个类型中出现，也不能仅凭名称相同判定为服务器同质组件。

## 7. 总体判定

本次审查确认：按共同读写者、变更原因和生命周期拆分组件是合理的；按旧类继承关系、字段名称或数据类型相似度进行合并是不合理的。

最明确的合理拆分包括：

- Health / MobState / Defense / Immunity
- Projectile Definition / Behavior / Lifetime / Owner / Damage
- InputIntent / Velocity
- Inventory / Hands / Container
- ItemDefinition / Stackable / Equipment / Weapon
- Targeting / NPC AI
- EntityIdentity / EntityReference
- StatusEffects / TimedStatusEffect
- Collider / 碰撞结果 / 碰撞策略

本报告只对这些组件之间是否应当拆分作出判断。
