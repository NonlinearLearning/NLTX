# 子系统 Markdown 编写指南

## 目标

本指南服务于 Version4 的代码理解和目标框架设计。它的产物是从现有类中抽出的
长期子系统地图，用于回答状态实际属于哪里、类中哪些成员应归为同一职责；
它不是 ADR、迁移计划、迁移批次、改造任务书或整体执行流程说明。

每份子系统文档必须让读者无需先读完整源码就能回答：

1. 它从哪些类、字段、属性和方法簇中抽取？
2. 它负责什么，明确不负责什么？
3. 它拥有哪一组状态，字段和属性的生命周期分别是什么？
4. 它依赖谁，谁依赖它，哪些访问方向不应该存在？
5. 当前代码为什么把这些职责混在一起，以及目标框架为何要划出这条边界？

## 资料依据

| 来源 | 可复用的写法 | 用于本仓库的规则 |
| --- | --- | --- |
| [Microsoft Learn: Common web application architectures](https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures) | 按职责划分逻辑层，并限制依赖方向以降低变化影响。 | 以责任和依赖定义系统，不能按文件夹、类名或字段前缀定义。 |

| [arc42: Runtime View](https://docs.arc42.org/section-6/) | 用少数代表性场景解释构件交互，而非罗列全部调用。 | 整体执行场景放入独立 `execution/` 文档；子系统卡只链接相关场景，不复述流程。 |

资料访问日期为 2026-09-02。它们用于提炼文档结构，不要求 Version4 采用
微服务、DDD、Clean Architecture 或特定框架。

## 类拆分索引模板

先为字段集中的源类建立 `class-decomposition/<命名空间.类型>.md`。它是调查索引，
只回答“这个类里有什么混合责任，以及每块应链接到哪份子系统卡”，不解释全局流程。

```markdown
# `Terraria.<Type>` 类拆分索引

## 类职责现状
<用一段话描述此类为何成为混合点。>

## 成员分组

| 当前成员块 | 代表成员 | 当前混合原因 | 候选子系统 | 子系统卡 |
| --- | --- | --- | --- | --- |
| <字段/属性/方法相邻块> | `...` | ... | `<System>` | `../subsystems/NN-...md` |

## 不应拆分的核心

| 成员 | 原因 |
| --- | --- |
| `...` | <与实体身份、协议槽位或基础值对象不可分离的原因> |

## 跨类汇合点

| 候选子系统 | 本类贡献成员 | 其他贡献类 |
| --- | --- | --- |
| `<System>` | `...` | `Terraria.OtherType` |

## 待确认问题
1. ...
```

先完成 `Main`、`Player`、`NPC`、`Projectile`、`Item`、`WorldGen` 六个索引，
再根据多类成员的实际汇合关系创建子系统卡。整体启动和 tick 链由独立
`execution/*.md` 解释，类拆分索引和子系统卡只保留链接。

## 整体流程文档模板

整体流程文档放在 `docs/architecture/execution/`，负责解释“静态子系统如何在一次
运行中协作”。它不重新拥有字段，不重新定义子系统边界，也不复制某个方法的所有
分支。每个文档只选择一个有明确起点和终点的流程：启动、世界加载、单次游戏
更新、世界保存、网络收包或网络发包。

建议先建立一个入口索引，再建立 3 至 6 个流程文件：

```text
execution/
  README.md                         # 所有流程的入口、触发关系和阅读顺序
  startup-and-composition.md        # 进程启动到 Main 初始化完成
  world-load-and-save.md            # 世界文件加载与保存
  game-tick.md                      # 一次 DoUpdate 的阶段，不展开实体内部算法
  network-receive.md                # 收包、解码、状态分派
  network-send.md                   # 状态变更到发包
```

### `execution/README.md` 模板

```markdown
# Version4 执行流程地图

## 阅读顺序
1. 启动与组合
2. 世界加载与保存
3. 游戏 tick
4. 网络收包与发包

## 流程总览

| 流程 | 触发点 | 起点 | 终点 | 参与子系统 | 文档 |
| --- | --- | --- | --- | --- | --- |
| 启动 | 进程参数 | `Program.LaunchGame` | `Main` 就绪 | 运行环境、内容定义、实体存储、网络会话 | `startup-and-composition.md` |
| 游戏 tick | 游戏循环 | `Main.DoUpdate` | 本帧提交完成 | 世界会话、实体、物理、网络、客户端表现 | `game-tick.md` |

## 约定

- 字段的语义所有权以 `../subsystems/` 为准。
- 本目录只记录阶段、参与者、消息/状态流向和关键分支。
- 某一步的内部规则复杂时，链接到子系统卡或具体源代码，不在此复制算法。
```

### 流程文档的编写规则

1. **按触发点拆分，不按类拆分。** `Main.DoUpdate` 是 tick 文档的入口，尽管它会
   调用 Player、NPC、WorldGen 和网络代码；这些类不应各自复制一份 tick。
2. **每一行都必须有阶段边界。** 读者应能知道“何时进入、谁处理、产生什么结果、
   下一个阶段是谁”，不能只看方法名列表。
3. **交接写系统名，不写字段大表。** 写“世界会话向 NPC 生成规则提供时间和事件
   快照”，字段归属细节链接到 `subsystems/world-session.md`。
4. **保留关键分支，不展开常规算法。** 专用服务器分支、暂停分支、网络模式分支、
   加载失败和异常退出应被记录；复杂 AI 或生成算法只保留源码链接和输入输出。
5. **图不是默认要求。** 简短阶段表通常优于时序图。只有参与者超过三方、存在回路、
   或顺序容易误读时，才添加带编号箭头的 Mermaid 或 C4 动态图。

## 状态分类规则

字段归类的核心不是名字，而是生命周期和写入边界。写文档时必须先回答下表问题。

| 状态类别 | 判定问题 | Version4 的典型例子 |
| --- | --- | --- |
| 进程运行环境 | 进程启动时建立，所有世界共享，且不应写入世界存档吗？ | `Program.LaunchParameters`、日志、平台服务。 |
| 内容定义 | 是否按 ID 查询、在内容初始化时填充、通常不随世界变化？ | `Main.tileSolid`、`Main.projHostile`、`Main.persistentBuff`。 |
| 世界会话 | 是否随一个世界加载/卸载，且会影响世界规则、时间或事件？ | `Main.worldName`、`Main.time`、`Main.raining`、`NPC.downedBoss1`。 |
| 地图与实体存储 | 是否通过固定槽位或坐标索引保存当前世界的对象？ | `Main.tile`、`Main.npc`、`Main.player`、`Main.projectile`。 |
| 实体实例 | 是否随着一个 Player、NPC、Projectile 的创建和销毁而存在？ | `NPC.ai`、`NPC.life`、`Player.inventory`、`Player.buffTime`。 |
| 网络会话 | 是否描述连接、收包、发包、同步节流或客户端身份？ | `Main.myPlayer`、NPC 的 `netUpdate` 与同步状态。 |
| 客户端表现 | 是否只为输入、UI、相机、渲染或音频而存在，专用服务器不应拥有？ | 鼠标悬停、界面缩放、画面动画缓存。 |
| 每帧派生值 | 是否可以从本帧世界和实体状态重新计算，不应持久化？ | `Main.CurrentFrameFlags`。 |

一个成员可能被多个系统读取，但只能有一个语义所有者。例如 `NPC.downedBoss1`
虽声明在 `NPC`，但它随世界保存、影响生成条件、并不属于一个 NPC 实例，因此
语义所有者是世界长期进度；`NPC.ai` 则属于 NPC 实例运行时状态。

## 图、表与细节的取舍

| 场景 | 适合的表达 | 不应使用的表达 |
| --- | --- | --- |
| 系统总览 | 一张一级系统关系图或依赖表。 | 把所有字段塞进总览图。 |
| 一个系统的字段归属 | 状态所有权矩阵。 | 只有长段落的字段罗列。 |
| 初始化、tick、保存或网络顺序 | 独立 `execution/*.md` 中的编号文字流程或简短时序图。 | 在每份子系统卡中复制流程。 |
| 三个以上内部构件有稳定关系 | C4 风格组件图。 | 没有箭头语义的装饰性方框图。 |
| 复杂算法 | 指向源码位置并说明输入、输出和不变量。 | 用文档重写所有分支。 |

## 对现有草案的收缩方式

现有三份 `*-split-draft.md` 可以保留为调查材料；形成正式子系统卡时只吸收事实和
边界结论，不携带实施、兼容、回退或决策记录章节。

| 现有草案 | 正式系统卡应保留的内容 | 应移除或另存的内容 |
| --- | --- | --- |
| `world-session-state-split-draft` | 世界描述、规则、时间天气、事件长期进度及其字段归属。 | tick 场景、迁移顺序、兼容门面、审核决策。 |
| `content-definition-catalog-split-draft` | ID 定义表、初始化位置、可变性边界和查询能力。 | 目录替换步骤、冻结时机策略。 |
| `entity-store-and-runtime-state-split-draft` | 槽位存储、Player/NPC 生命周期、状态子域、网络语义。 | 验证批次、替换顺序。 |

## 最低完成标准

一份子系统 MD 达到以下条件即可进入总览，不需要等待框架代码实现：

- 有明确范围和排除范围；
- 有至少三个真实源码位置，而不是只依据字段名称；
- 写清一个一句话职责，以及至少一个“不负责什么”；
- 所有关键状态均标有生命周期和语义所有者；
- 列出关联流程文档的链接，但不在本文件重述整体运行顺序；
- 说明与至少一个相邻系统的读写方向；
- 未确认项显式列出，不能伪装为完整结论。
