# 非函数式编码副作用隔离规范

状态：草案（用于评审）  
适用：C# 命令式/面向对象代码、后台任务、协议和基础设施调用

本文是一份架构无关的建议性编码指导。它不要求采用特定的架构、框架、对象模型、目录、
依赖注入语法、消息组件或调度方案，也不要求把所有代码改写成纯函数式风格。

本文使用以下措辞：

- **建议**：通常有助于降低副作用风险，应作为默认做法；
- **风险场景下应当**：只有在对应风险存在时适用；
- **底线**：涉及安全、数据完整性、资源泄漏或不可恢复损坏时，不应违反。

## 1. 副作用的识别范围

副作用是函数或方法除返回值外，对外部可观察状态产生读取、写入或时序影响的行为。它包括：

- 读取或修改共享状态；
- 数据库、文件、网络和操作系统 I/O；
- 获取当前时间、随机数或新标识符；
- 启动任务、线程、定时器或延迟回调；
- 发布事件、消息、日志、指标、UI 或音频效果；
- 依赖延迟执行、枚举次数或回调顺序的行为。

局部变量的创建和只基于参数的计算本身不是副作用。“只读”也不自动表示无副作用：读取数据库、时间、随机源或共享状态仍会观察外部状态。

本定义只用于识别风险，不要求使用特定代码结构。

## 2. 基本原则

1. 让外部输入、可变状态和 I/O 对调用方可见、可测试、可追踪。
2. 可复用的规则、查询和计算逻辑，建议写成只依赖显式输入的确定性计算。
3. 计算与效果执行建议分开；负责状态写入或外部 I/O 的代码可以保留副作用，但应明确说明这些效果。
4. 时间、随机数、标识符、配置和环境信息建议作为显式输入或可替换依赖提供。
5. 不要把“恰好一次”当作默认事实；无法证明时，应说明实际采用的是至多一次、至少一次或允许重复。

## 3. 副作用登记建议

涉及外部读取、状态修改、异步工作、消息、持久化、缓存或可观察性效果的方法，建议在变更说明、测试说明或代码契约中记录：

```text
读取：数据库 / 文件 / 网络 / 时间 / 随机数 / 环境变量 / 共享状态
写入：状态 / 消息 / 缓存 / 日志 / 指标 / UI 等
责任边界：负责执行效果、处理失败和释放资源的代码
顺序：相对于其他效果的先后关系（如有）
失败：明确失败 / 超时未知 / 取消 / 重试或补偿方式
重复：是否允许重复、如何去重或为何无需去重
```

这是一种记录格式示例，不要求使用特定文件、属性、接口或类名。小型局部修改可以在代码评审描述中简要填写；高风险变更应在测试或变更记录中保留完整说明，并关联至少一项与主要风险相符的验证证据。证据可以是自动化测试、集成测试、可重复的手工步骤、运行诊断，或当前不可执行验证的原因说明。

满足以下任一条件的变更可视为高风险：

- 写入持久化数据，或同时改变多个可观察状态；
- 发送可能重复、丢失或延迟的消息；
- 跨线程、跨进程或跨请求共享或修改状态；
- 超时后可能无法确认操作结果；
- 启动后台任务、定时器或延迟回调；
- 涉及资源租借、释放或长生命周期连接；
- 失败后需要人工恢复、补偿或审计。

## 4. 可复用计算与显式输入

- 可复用的规则、计算查询和计算函数，建议只接受参数、不可变数据或显式配置。
- 这类函数不应直接访问文件、数据库、网络、线程、进程环境、系统时钟或随机 API。
- 计算可以返回结果、诊断信息或“待执行动作”；具体如何执行由调用边界决定。
- 不要把会写状态的委托、回调或可变对象藏进配置和数据模型来绕过说明。
- 可预期的业务拒绝建议使用结果值或明确错误码；外部依赖失败不应伪装成业务拒绝。

本文中的“计算查询”只基于已提供的数据判断、筛选、投影或计算，适用本节的显式输入建议。“外部查询”从数据库、文件、网络、时钟、随机源或共享状态读取，属于副作用，适用登记、延迟执行、资源和失败处理建议。类型、目录或方法名中含有 `Query` 不自动决定它属于哪一类，应按实际读取来源判断。

负责状态修改、事件发布、日志或外部 I/O 的系统不需要被强制纯化，但应使副作用集中在可定位的执行边界，并能解释其责任和失败行为。既有框架入口或遗留静态全局访问可以暂时保留在明确的外层边界；新的可复用计算不应新增这类隐式依赖，触及遗留访问时建议说明读取/写入范围和迁移风险。

## 5. 延迟执行与执行时机

`IEnumerable<T>`、LINQ 查询、迭代器、事件回调和异步 continuation 可能在创建点之后才执行。存在下列风险时应当显式处理：

- 查询在枚举时才读取外部状态，或多次枚举导致重复读取；
- 返回延迟对象后，数据库连接、文件流或其他资源已经释放；
- 回调或 continuation 在原调用方完成、取消或资源释放后，仍继续修改状态或触发效果；
- 查询表达式混入写入、网络调用、日志推进或其他隐藏副作用。

需要一次性结果时，建议在明确边界物化（例如 `ToArray()` 或 `ToList()`），并记录执行时机。纯查询对象不应携带隐藏写入行为；如果延迟执行是有意设计，应说明生命周期和可重复执行语义。

普通且受当前调用生命周期控制的 `await` 不需要因为语法本身额外登记。只有 continuation 捕获可能失效的可变状态、资源租借或请求上下文，跨越调用生命周期，触发新的外部效果，或其线程、顺序、异常传播会改变可观察结果时，才应按延迟执行风险处理。

## 6. 状态与可变数据

- 建议明确每个可变状态的写入责任边界，其他代码通过受控操作或明确请求提出变更。
- 不要直接返回内部可变集合；跨边界返回值建议使用不可变快照或防御性复制。受控只读视图、租借或切片也可以作为替代方案，前提是调用方不能藉此修改内部状态，并且所有权、有效期、线程安全和失效条件已说明。
- 只读接口不自动代表深度不可变；集合、字典及其元素都要考虑间接修改风险。
- 修改状态前建议校验前置条件、版本和不变量，并对冲突提供可识别结果。
- 并发代码应说明采用的同步方式及取消、关闭、超时期间的行为。

资源泄漏、数据竞争、越权写入或不可恢复损坏属于底线：不能因为接口形式看起来只读或“通常不会并发”就忽略这些风险。

## 7. 变更表示与提交

当变更跨越模块、线程、进程或可靠性边界，或者需要排序、重放、审计、重试、去重或恢复时，建议把变更表示为可追踪的显式请求、事件或其他等价记录。

显式请求、command、事件、事务或两阶段规划只是可选手段，不是本规范规定的固定类型。选择实现方式时，应说明：

- 变更的目标和责任边界；
- 是否需要稳定顺序或版本检查；
- 重复投递、部分成功和失败恢复如何处理。

同一调用范围内、不需要独立排序或恢复的局部更新，可以由明确责任边界直接完成。不要为了形式统一给每个局部字段更新增加不必要的消息或请求层。

## 8. 外部 I/O、资源与依赖

- 外部能力建议通过显式依赖、受控边界或可替换服务提供；具体采用接口、注入服务、上下文对象或其他方式由项目决定。
- 业务代码不应在使用点自行创建难以管理的连接、客户端、线程、定时器或进程级资源。
- 协议适配代码可以处理序列化、容量、超时、取消和技术错误，但不应偷偷改变业务规则。
- 资源应由创建者或明确责任边界释放，成功、异常和取消路径都要覆盖。
- 技术异常建议转换为稳定、可测试的错误类别，不要让调用方依赖第三方库的异常文本。

安全、资源释放和数据完整性相关的依赖错误属于底线；不能用“以后再处理”掩盖未关闭的资源或未定义的失败结果。

## 9. 异步、取消、超时与重试

- 纯计算通常保持同步；外部 I/O 是否异步由调用场景和库能力决定，但取消语义应当明确。
- 取消是协作式请求。取消后不应无意启动新的效果；已经开始的操作不能假定可撤回。
- 超时不等于失败。结果未知时，建议通过查询、幂等信息或补偿流程确认，不要盲目重复执行。
- 当外部操作无法取消、取消只影响本地等待，或取消后的远端结果无法确认时，不要把它标记为“已安全取消”。建议在副作用登记中说明实际语义，并按结果未知评估确认、重复或补偿风险。
- `OperationCanceledException` 不应被无条件当作普通失败吞掉或重试。
- 存在重试风险时，应说明上限、退避、截止时间、重复处理方式和不可重试的错误类别。
- 技术层与业务层重试的总次数应可估算，避免无界叠加。
- 后台任务建议记录开始、成功、失败、取消和重试，并说明进程退出时的排空、取消或丢弃行为。

## 10. 持久化、消息、缓存与可观察性

- 持久化写入和消息发布的先后关系应明确；不能把两个连续调用都返回成功当作原子性证明。
- 消息可能重复、丢失或延迟时，风险场景下应记录投递语义、版本和去重/补偿方式。
- 发布确认丢失时，应按实际投递语义处理潜在重复，不要为了“看起来不重复”删除已确认的业务状态。
- 缓存只应保存允许过期或丢失的数据；失效、并发更新和版本覆盖规则应有说明。
- 日志、指标、追踪和诊断应只观察结果，不应通过回调推进业务状态或递归触发另一条效果链。

## 11. 测试与静态检查建议

按风险选择测试重点：

- 纯计算：边界、拒绝、不变量和确定性；
- 外部 I/O：明确失败、超时未知、取消、协议错误和资源释放；
- 可重试或可靠消息：重复、去重、部分成功和恢复；
- 后台任务：退出、排空、取消、失败记录和重试上限；
- 延迟执行：枚举次数、资源生命周期和执行时机。

静态检查或代码评审可以关注：隐式全局状态、空异常捕获、纯计算直接 I/O、可变集合泄漏、未说明的延迟执行和无界重试。

## 12. 底线检查清单

- [ ] 没有因未关闭资源而造成资源泄漏。
- [ ] 没有因未处理并发或取消而造成数据损坏或越权写入。
- [ ] 外部调用的失败、超时未知和取消结果没有被无条件吞掉。
- [ ] 可靠性边界上的重复、丢失或部分成功风险已有可恢复处理。
- [ ] 日志、指标和诊断不会改变业务结果。
- [ ] 纯计算没有偷偷读取隐含外部状态或执行 I/O。

## 13. 参考资料定位

本规范的原则依据包括函数式编程中的不可变数据、显式输入、命令式外壳和效果描述，以及 .NET 对依赖管理、取消和 LINQ 延迟执行的官方说明。

SS14/RobustToolbox 的源码仅作为工程实践参考：其系统可以通过依赖取得时钟、随机数、日志、音频、物理和地图服务，并在同一执行边界中查询、修改状态、发布事件、生成或删除实体。这证明副作用可以集中在明确边界内管理，但不证明任何特定架构、目录、类型或 API 是唯一正确方案。
