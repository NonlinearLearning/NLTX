# ECS 拆分参考模式

本参考综合 ECS 设计类 skill 的可迁移经验，不绑定 Unity、Bevy 或某个具体 ECS API。

## 组件粒度

把 ECS 看作按列组织的数据表：Component 是列，Entity 是行，Query 是筛选器，System 是批处理逻辑。
组件按系统访问模式、生命周期和语义内聚度分组。存在“系统只需要 A、不需要 B”时优先考虑拆分；若拆分制造跨组件不变量和复杂查询，则保留语义单元。

## 数据流

- Component 保存数据，不跨实体执行业务行为。
- System 通过 Query/输入读取并表达写入和状态转换。
- Query 只做纯派生计算、筛选和资格判断。
- Commands 表达结构变化或意图，不能让任意对象字段被隐式修改。
- Projection 将内部状态转换为网络、持久化、日志或查询视图，视图字段不能反向驱动权威行为。

## 性能与一致性

不要为了“数据导向”而过度拆分。大量实体、每帧处理和 CPU 受限时，优先检查批处理、查询范围和结构变更成本；同时为缓存定义所有权、失效条件和一致性验证。系统只有在数据访问不冲突时才可并行，必须的先后关系要显式声明。

## 迁移检查

OOP 转 ECS 时，先保留行为语义和验证，再移除继承依赖。临时预测对象、客户端表现对象和兼容对象不要默认注册为权威持久实体。实体引用、持久化标识、网络标识和外部账户标识必须分别建模。
