# ECS 文件组织设计约束

## 1. 文档状态

| 项目 | 约束 |
| --- | --- |
| 适用范围 | 本仓库全部 ECS、领域模型及其配套源码、测试和文档 |
| 规范性质 | 正式设计约束 |
| 强制入口 | 根目录 `AGENTS.md` |
| 适用阶段 | 新增、移动、拆分、合并和重命名文件时 |

本文件规定文件和目录的组织方式，不规定具体字段、组件 API、系统算法、运行时框架或
业务规则。若某项变更同时涉及数据模型或架构边界，必须另行记录设计决策。

## 2. 核心原则

### 2.1 领域优先

目录首先表达游戏领域、能力或规则，其次才表达文件职责。维护者应能够通过领域目录
定位一项功能的主要状态和相关访问代码。

推荐：

```text
<代码根>/
  Movement/
  Physics/
  Inventory/
```

不推荐将所有领域横向切散为长期全局入口：

```text
<代码根>/
  Components/
  Systems/
  Queries/
  Events/
```

### 2.2 小目录扁平化

领域规模较小时，文件直接放在领域目录中；不要为目录模板完整性创建空的
`Components/`、`Queries/` 或其他职责子目录。

### 2.3 子目录按需引入

领域内部只有在出现以下至少一项时，才增加子目录：

- 稳定且可独立理解的职责聚合；
- 明确的依赖或访问边界；
- 已经影响导航效率的文件规模；
- 可独立测试、发布或迁移的子模块。

子目录的引入必须基于实际文件和不变量，并在变更说明中记录影响。不得根据未来猜测
预建空目录。

### 2.4 组合优先

ECS 实体通过组件组合表达能力，不通过 `PlayerEntity`、`NpcEntity`、`ProjectileEntity`
等继承树聚合共享状态。共享组件按其表达的能力归属，而不是按第一个使用它的实体类别
归属。

### 2.5 一致命名

一个核心公开类型对应一个 PascalCase 文件；文件名应与类型名一致。目录名使用
PascalCase，避免无语义的 `Misc`、`Data`、`Helper`、`Utility`、`Utils` 和泛化
`Manager` 目录或类型。

## 3. 仓库级目录分层

根目录按交付边界组织，而不是按个人工作流或临时任务组织：

```text
/
  src/                 # 可复用库、共享领域、服务器、客户端和工具源码
  Test/                # 可执行验证项目与测试夹具
  dome/                # 独立工作区；其内部继续遵循本约束
  架构设计/            # 已确认的架构与设计约束
  约束/                # 编码、构建和流程约束
  Build/               # 构建脚本、生成物和缓存，不放业务源码
  .agent-workplace/    # Agent 私有过程产物，不作为业务源码入口
```

### 3.1 生产代码

- `src/` 存放正式生产源码，按项目边界和领域组织。
- 共享代码放在 `Share` 或等价的共享项目边界内；服务器、客户端和工具代码不得反向
  混入共享领域。
- `dome/` 是独立工作区时，使用 `dome/src/`、`dome/Test/` 和 `dome/docs/` 的内部边界；
  不把其源码平铺回根目录 `src/`。

### 3.2 测试与验证

- `Test/` 与生产项目平行，测试项目名称应能对应被验证的生产项目或领域。
- 测试按领域或验证目标组织，不建立全局无语义的测试杂物目录。
- 测试夹具、快照和记录数据放在对应测试项目内，生成性输出放入 `Build/` 约定目录。

### 3.3 文档

- `架构设计/` 只放已确认的架构、设计和约束文档。
- 临时草稿、审查过程和未归档记录放在 `.agent-workplace/` 或对应流程目录，不冒充正式
  约束。
- 正式约束应在 `AGENTS.md` 或其他项目入口中提供链接，避免只靠文件名发现。

## 4. ECS 领域内部组织

### 4.1 领域目录

领域目录使用游戏语义命名，例如 `Entity`、`Movement`、`Physics`、`Player`、
`Npc`、`Projectile`、`Tiles` 和 `Liquid`。领域命名必须能够回答“这些文件共同表达哪项
能力或规则”。

### 4.2 组件文件

组件直接放在所属领域目录，除非该领域已经满足第 2.3 节的子目录条件：

```text
<代码根>/
  Entity/
    EntityIdentityComponent.cs
    LocationComponent.cs
  Movement/
    VelocityComponent.cs
  Physics/
    ColliderComponent.cs
```

组件目录只放持续的实体或世界状态。组件不因包含相似字段就跨领域合并，也不承载跨实体
行为。

### 4.3 查询文件

查询与其主要读取的能力领域放在一起。小型查询直接放领域根目录：

```text
Physics/
  ColliderComponent.cs
  EntityGeometryQuery.cs
  EntitySpatialQuery.cs
```

当查询数量、访问边界或实现职责稳定分化后，才允许增加 `Queries/`、`Geometry/` 或
`SpatialIndex/` 等子目录；子目录名称必须表达真实职责，不得只重复技术后缀。

### 4.4 其他职责

本约束不强制规定 System、Event、Command、Snapshot、Definition 的统一目录名称。它们
仍必须遵循领域优先和按需细分原则：先归属领域，再根据实际规模决定是否建立职责子目录。
某个项目若需要跨领域统一的调度或注册入口，应在该项目的架构文档中单独声明，不能由
文件枚举顺序隐式决定执行顺序。

## 5. 共享组件归属规则

新增组件按以下顺序归属：

1. 只属于一种实体类别：放入该实体类别领域，例如 `PlayerInputComponent` 放入 `Player/`。
2. 表达多个实体共享的明确能力：放入能力领域，例如 `VelocityComponent` 放入
   `Movement/`，`ColliderComponent` 放入 `Physics/`。
3. 几乎适用于所有实体且不表达特定玩法：放入 `Entity/`。

禁止建立泛化 `Shared/Components/` 目录作为暂时无法归属的收容处。无法确定归属时，
先澄清组件的权威状态、主要读写者和生命周期，再决定目录。

## 6. 项目边界与端别扩展

当同一领域出现共享、服务端和客户端实现时，保持领域名一致，在平行项目中表达端别：

```text
src/
  Shared/
    Movement/
  Server/
    Movement/
  Client/
    Movement/
```

只有真实存在独立代码、依赖或发布边界时才拆分端别项目；不得为模仿大型项目而提前
创建空的 `Shared/Server/Client` 目录。端别拆分不改变领域名称，也不允许服务端或客户端
专属状态回流到共享层。

## 7. 依赖、命名空间与迁移

- 目录路径表达归属，不自动决定 C# 命名空间；命名空间变更必须作为独立 API/依赖变更
  评估。
- 目录移动应优先保持行为、公共 API 和命名空间不变，除非变更目标明确要求同步调整。
- 跨领域访问通过稳定的公共类型、只读查询、命令、事件或接口完成，避免直接依赖对方
  的内部实现。
- 迁移按小批次进行：先记录源路径与目标路径，再移动文件，随后修复引用并执行受影响
  项目的验证。
- 不得依赖文件名排序、目录枚举或项目文件顺序表达运行时执行顺序。

## 8. 新增与迁移验收

每次新增、移动、拆分或合并 ECS 文件时，必须检查：

- [ ] 领域目录表达了游戏能力或规则，而不是只有技术类别。
- [ ] 小领域没有为了模板完整性创建空职责子目录。
- [ ] 新增子目录有稳定职责、规模或依赖边界依据。
- [ ] 共享组件按能力归属，没有按实体类别复制同义状态。
- [ ] 一个核心公开类型对应一个同名 PascalCase 文件。
- [ ] 查询与主要读取的领域相邻；跨领域访问边界清晰。
- [ ] 目录移动没有未经批准地改变命名空间、公共 API 或运行时行为。
- [ ] 未把生成物、临时草稿或 Agent 过程文件放入生产源码目录。
- [ ] 受影响项目按仓库构建约束完成验证；输出位于 `Build/bin/`。
- [ ] 变更说明包含源路径、目标路径、依赖影响和回滚方式。

## 9. 适用优先级

发生冲突时，适用以下优先级：

1. 安全、数据完整性和架构边界；
2. 项目或目录级 `AGENTS.md` 的更具体约束；
3. 本文件的仓库级 ECS 文件组织约束；
4. 一般命名和格式偏好。

任何例外都必须在对应架构文档或变更记录中说明原因、范围和撤销条件。
