## Simulation ordering and owner boundaries

WorldSimulationKernel owns its thread, tick commit, clock/snapshot boundaries, and a ConcurrentQueue of Action<WorldSimulationTickContext>. It drains commands before the world clock; commits a snapshot and runtime projection; then executes registered phases in enum order; and only then commits the tick. The queue stores delegates, so its API does not constrain closures from retaining session data or runtime handles.

The phase order in WorldSimulationPhase and the host registration is:

1. CommandDrain
2. WorldClock
3. SnapshotCommit
4. RuntimeProjection
5. Player
6. Npc
7. Projectile
8. WorldItems
9. TileEntities
10. WorldSystems
11. TickCommit

NPC natural spawn runs before the NPC active snapshot and slot update. A spawned NPC can therefore participate in the following NPC scan in that same phase, depending on its slot. NPC iteration scans slots in ascending order. Natural spawn consumes RuntimeMain.rand; NPC AI also uses both a seeded per-store Random and Main.rand at specific behaviors. Replacing this with archetype/chunk iteration would change RNG consumption and slot visibility.

Player update and scripted weapon use iterate the player array in slot order. Player update reads and commits movement, physics, lifecycle, and item-use values; weapon use may spawn a projectile, consume ammunition, and then commit item-use timing. ProjectileTickCoordinator scans regular projectile slots in ascending order and owns substep/tail rules. World item update scans world-item slots in ascending order, updates motion/expiry first, then tries players in player-array order and stops after the first applied pickup.

These are explicit scheduling contracts. A normal Arch query must not replace these traversals unless its results are first ordered by the same domain slot and the same spawn/commit boundaries are preserved.

## Old access semantics and ref/copy audit

- RuntimeNpcEntity and RuntimePlayerEntity are long-lived views that keep EntityRuntime plus RuntimeEntityHandle values across ticks. They expose many property reads and mutation methods; they are not Arch refs, but their future resolution must carry the owning session token.
- RuntimeProjectileStore.ReadComponent uses TryInspect to copy struct values, passes local values to domain calculations, then commits through TryEdit/TryEditComponents. This is an intentional copy/edit/commit path, not a write-through reference.
- RuntimePlayerStore.Update copies MovementStateComponent, mutates it, then assigns it back through the wrapper. Do not translate this into a discarded TryGet<T> local.
- RuntimeNpcEntity movement setters and the NPC/Player/Projectile edit paths use synchronous by-ref callbacks. No Arch ref should survive the callback, phase, or any Add/Remove/Destroy/create operation.
- RuntimeItemRegistry builds ItemMutationRevision from generic attachment/data revisions and uses versioned captures around stack/world-item commits. The source confirms a stale-write conflict use, but the generic ECS revision is not an acceptable second authority after migration.
- WorldItemReservationComponent and WorldItemReservationSystem already have domain ReservationId, expiry and ReservationRevision rules. NetworkWorldItemOwner rechecks that contract while applying synchronized item state. Preserve the named reservation owner and quantity checks; do not mechanically carry generic attachment revisions forward.
- NetworkWorldOwner and WorldSimulationKernel queue delegates, not raw refs by type. A delegate can still close over a handle/session. ProjectileTickContext and NPC task/relationship references carry values across synchronous steps or ticks and must be resolved against the current session/lifecycle owner.
- No Arch Entity or Arch integer is present in current DTO/protocol sources because this checkout has no Arch production integration. This is only a pre-migration baseline; re-run the DTO/serialization scan after integration.

## Explicit high-risk path to revisit

The source comment explicitly preserves accepted no-op behavior for missing, stale, inactive, or repeated packet-29 requests. That conflicts with the T4 request to explicitly reject stale/expired requests. Keep this as a T4-B2 blocker for a follow-up with T2/T3 lifecycle identity in hand; do not patch it against the current custom handle API.
