# 错误处理约束

状态：生效  
适用：`src/NSSLC/**`、`src/NSSLC.Server/**`、`src/NSSLC.Infrastructure/**` 的全部生产代码；
`Test/**` 中验证错误路径的验证项目  
上游依据：[错误处理机制选型研究](../../docs/research/2026-11-25-error-handling-mechanism-research.md)

本约束规定"失败如何被表达、如何被检查、如何穿越边界"。它不规定依赖注入语法、不规定具体类型命名，
只规定六件事：分类线、错误模型、分层编码、码空间治理、载荷与结果未知、C# 落地形态。

本文使用以下措辞：

- **必须**：违反即视为缺陷，评审应退回；
- **应当**：默认做法，偏离须在变更说明或代码注释中写明理由与撤销条件；
- **建议**：通常更安全，不作为退回理由；
- **禁止**：与**必须**同级。

本文件与 [非函数式编码副作用隔离规范](非函数式编码副作用隔离规范.md) 的关系：该规范 §4
"可预期的业务拒绝建议使用结果值或明确错误码"、§8 "技术异常建议转换为稳定、可测试的错误类别"
是本文第 1、6 节的输入端；本文把这两条在本项目范围内从"建议"收紧为**必须**，其余部分不冲突时
仍以该规范为准。跨域失败的表达同时受 [ECS 系统输入边界约束](ECS系统输入边界约束.md) 约束：
域间失败走请求/结果组件，不直接调用对方的状态修改方法。

## 术语

- **预期失败**：调用方必须处理的正常结果，例如库存满、槽位不兼容、内容定义缺失、限流拒绝。
- **缺陷**：程序自身不变量被破坏，例如索引越界、空引用、第三方库契约破裂。
- **技术异常**：外部依赖不可用、IO 失败、协议帧损坏等由环境引起、而非由业务规则引起的失败。
- **结果未知**：操作可能已经发生但无法确认，例如超时、发送后连接断开。
- **取消**：协作式的提前终止请求，既不是失败也不是成功。
- **码**：可比较、可落盘、可跨版本的整数或封闭枚举值，用于机器判别。
- **载荷**：随失败一起返回的结构化上下文，例如槽位号、实体 id、诊断列表。
- **错误模型**：分类学、码空间、语义、转换规则的合集，全仓库唯一。

## 1. 先分类，再选机制

失败进入哪条通道，按顺序问五个问题，命中即停：

1. **这是缺陷吗？** 是 → 断言、`InvalidOperationException`、`ArgumentOutOfRangeException` 等，
   不进入错误处理通道，不设计返回值。
2. **这是取消吗？** 是 → `OperationCanceledException` 或等价取消结果，不当作普通失败吞掉、不重试。
3. **这是技术异常吗？** 是 → 在所在层转换为**稳定类别**（码或封闭枚举），禁止让第三方异常文本
   泄漏进领域层。
4. **调用方要按原因分支，或需要载荷吗？** 需要 → 类型化结果（封闭枚举 + 可选载荷）。
5. **否则** → 布尔或纯分类枚举即可，不要为了"看起来严谨"发明载荷。

错配对照（均为**禁止**）：

| 错配 | 为什么禁止 |
| --- | --- |
| 用异常表达库存满、槽位不兼容等业务拒绝 | 把可预期结果变成控制流异常，强制力用错方向，热路径还要付栈展开成本 |
| 用返回值表达索引越界、空引用 | 让 bug 混进业务失败通道，调用方无法区分"该重试"与"该修代码" |
| 用布尔表达需要分支的拒绝 | 调用方只能记日志，无法按原因处理；原因被迫塞进日志文本 |
| 用自由文本代替码 | 文本不稳定、不可比较、不可统计、随文案改动而漂移 |
| 把 `OperationCanceledException` 当失败处理 | 取消若被当失败重试，会重复执行已经开始的操作 |

## 2. 统一错误模型

统一的是**错误模型**，不是编码。模型包含四项，全仓库只允许一份定义：

1. **分类学**：severity（fatal / error / warning / info）、facility（哪一层产生）、retriable 与否。
   severity **必须**至少能区分"内容不可用"与"可用但可疑"——`LvcsDiagnosticSeverity` 的
   `Warning` / `Error` 即最小合格形态。
2. **码空间**：谁分配、区间怎么划、废弃码怎么处理，见第 4 节。
3. **语义**：每个码或变体的确切含义，写在定义处的 XML 注释里，不写在其它文档里。
4. **转换规则**：层与层之间如何映射、损失什么、保留什么，见第 3 节。

**必须**避免同一失败事实存在两套并行语义。当前的反例是小节 7 的
`WorldInteractionResultComponent`：状态枚举管"成没成"，失败原因另走自由文本。

## 3. 分层编码

| 层 | 编码 | 形态要求 |
| --- | --- | --- |
| L1 领域内（同一域的系统与组件之间） | 类型化结果 | 封闭枚举 + 载荷，穷尽匹配 |
| L2 模块 / 程序集边界（Share 与 Unshared 之间） | 收敛的封闭枚举 | 变体数量受控，新增按 append-only 处理 |
| L3 系统边界（协议、磁盘、FFI） | 稳定整数或封闭码 + 可选 detail 块 | 码只增不改；detail 自描述版本 |
| L4 观测（日志、指标、诊断、文案） | 码作稳定键 | 文案表按码查，不按消息文本匹配 |

转换纪律：

- **必须**只允许从内向外（L1 → L2 → L3）单向转换，每层转换有损且必须写明损失了什么。
- **必须**禁止反向恢复：由码反推 L1 具体变体只在查表且校验通过时允许，不得凭绝对值猜测。
- **必须**为每张跨层映射表写测试；新增 L1 变体而未更新映射时，测试必须失败。

## 4. 码空间治理

- **必须** append-only：码一旦发布只增不改不复用。废弃语义用"标记废弃 + 保留分配"表达。
- **必须**为未知码定义降级规则：旧读者遇到不认识的高位（扩展码 / facility）时，按主码或
  facility 降级为类别失败，不得静默当作成功。
- **应当**让码自带分类学：SQLite 式"主码是扩展码前缀"，或 HRESULT 式"severity / customer /
  facility / code 位域"。整码能承载层级时，不需要额外再传一份 category 字段。
- **必须**把**内部诊断码**与**协议码**分开：
  - 内部诊断码只在本进程内用于日志、指标与断言，**不承诺**跨版本稳定；
  - 协议码是跨进程契约，**必须**与协议版本一起治理。
  - 判定口径：一个码只有被写进帧、存档或其它持久载体时才是协议码。当前
    `ProtocolErrorCode`（15 个值，仅 `src/NSSLC.Network` 四个文件使用）、
    `PacketFrameErrorCode`、`PacketReadErrorCode` 均**未**被序列化到线路，属内部诊断码，
    不得对外宣称是协议契约。
- **建议**建立单一码注册表承载 facility 与区间分配，避免第 7 节所示的分散局面继续扩大。

## 5. 载荷、部分成功与结果未知

- **必须**让载荷承载"够用的定位信息"：哪个实体、哪个槽位、哪个字段、哪一条内容。
  拒绝只带一句 `"failed"` 等于没带。
- **必须**在需要一次报全全部问题处使用聚合诊断形态，例如内容加载校验：
  `Result<T, IReadOnlyList<Diagnostic>>`。当前合格样板是 `LvcsLoadResult<T>` +
  `LvcsDiagnostic`（severity / family / id / field / message / source），它把"位置"留成
  基础设施提供的自由文本、领域层从不解释，因此没有把文件模型带进领域。
- **必须**把"部分成功"表达成显式字段，不要用布尔 `true` 掩盖只完成了一部分：
  `InventoryTransferResult(Succeeded, Quantity, Failure)` 用 `Quantity` 表示实际提交量，
  是标准形态。
- **必须**区分"失败"与"结果未知"。结果未知**不得**按失败重试，**不得**声称已安全取消。
  `TransportSendCertainty` 的 `OutcomeUnknown` 是该语义的一等表达，应当保留并被消费者正确处理。
- **应当**让失败值可以跨 tick 保存：错误是普通值，可以存进组件、排队、延迟处理。

## 6. C# 落地形态

C# 没有 `#[must_use]`，强制力靠约定与测试补足：

- **必须**用类型名表达成功/失败语义，例如 `*Result`、`*Receipt`、`*Rejection`；不返回裸
  `bool` 表达可分支的拒绝。
- **必须**让失败值不可被静默丢弃：调用方要么消费，要么显式丢弃并写明理由
  （`_ = ...` 后面必须跟注释）。**建议**在可空的失败结果上引入静态分析标注或评审检查项。
- **必须**用构造器强制不变量，把"失败必带原因"变成构造期失败而不是运行期空检查。
  `SendReceipt` 在构造器里拒绝 `Failed` 却无 `ErrorCode` 的组合，是本文推荐形态。
- **必须**把技术异常转稳定类别后再跨层。当前合格样板：`PacketFrameFormatException` 携带
  `PacketFrameErrorCode`，既保留 `IOException` 家族语义，又给调用方一个可判别的码；
  这是"边界层仍可用异常，但异常必须自带稳定码"的形态，允许出现在 L3。
- **禁止**在领域层（L1）用异常表达业务拒绝，**禁止**用 `catch (Exception)` 空吞。
- **禁止**让码型枚举直接充当线路格式。要把码送上线路时，**必须**显式写协议字段、写明版本与
  未知值处理，而不是把枚举值当协议的一部分。

## 8. 验收清单

新增或修改失败路径的变更，评审时逐条核对：

- [ ] 失败已按第 1 节五问归入正确通道，没有异常/返回值错配。
- [ ] 可分支的拒绝返回类型化结果，不是裸 `bool`，不是自由文本。
- [ ] 失败值带够定位载荷；聚合场景一次报全全部问题。
- [ ] 跨层转换是 L1 → L2 → L3 单向的，损失已写明，映射表有测试锁死。
- [ ] 新增码是 append-only，未复用旧值，未知码有降级规则。
- [ ] 内部诊断码没有被当作协议契约；进入线路的码已显式定义协议字段与版本策略。
- [ ] 结果未知没有被压平成失败，没有被盲目重试。
- [ ] 取消没有被当作普通失败吞掉或重试。
- [ ] 技术异常已转换为稳定类别，调用方不依赖第三方异常文本。
- [ ] 失败值没有静默丢弃；显式丢弃处有理由注释。
