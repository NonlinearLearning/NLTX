# 调试工具客户端操作手册

本手册说明 NLTX 网络联调所用的「无 UI 调试客户端」工具链：服务器、真实客户端夹具、
抓包代理与裸包监视器的构建、启动、判读与排障。内容以工作区 2026-11-22 的实际源码与
`Build/runtime/` 运行证据为准；参数以源码为准，路径以仓库根目录为基准。

| 项目 | 说明 |
| --- | --- |
| 适用范围 | `src/NSSLC.Server`、`D:\TRbackup\最新的客户端` 的 `-networktest` 夹具、`Build/runtime/HeadlessPacketProxy`、`Build/runtime/RawNpcMonitor` |
| 建立日期 | 2026-11-22 |
| 前置阅读 | [开发协作与变更约束](../项目约束/开发协作与变更约束.md)、[构建与验证约束](../项目约束/构建与验证约束.md) |

## 1. 工具构成

| 组件 | 位置 | 作用 |
| --- | --- | --- |
| NSSLC ECS 服务器 | `src/NSSLC.Server/Program.cs` | 监听 `127.0.0.1:7777`，加载真实 `.wld`，运行 ECS 权威模拟 |
| 最新客户端（无 UI 夹具） | `D:\TRbackup\最新的客户端\bin\Debug\net40\Terraria.exe` | `-networktest <场景>` 启动，复用原版包解析器走完整握手/世界/出生链路，不创建窗口和图形设备 |
| HeadlessPacketProxy | `Build/runtime/HeadlessPacketProxy/` | 单连接 TCP 中继，逐帧十六进制抓包，用于观察 C2S / S2C 时序 |

```text
                                        ├→ 127.0.0.1:7778 HeadlessPacketProxy → 127.0.0.1:7777 NSSLC ECS 服务器

```

## 2. 前置条件

- .NET SDK 版本由 `global.json` 指定（`net10.0`）；构建命令统一从仓库根目录执行。
- 世界文件默认 `src/World/科研.wld`（`8400×2400`，实测 `chests=493`）；任意受支持的
  WorldFile 都可以用显式路径替换。
- 端口 `7777`（服务器）与 `7778`（代理）空闲；服务器只绑定回环地址，没有对外监听选项。
- 客户端使用已构建的 `Terraria.exe`（2026-10-31 产物）；当前源码重建会失败，见第 8.6 节。

## 3. NSSLC ECS 服务器

### 3.1 构建

```powershell
dotnet build src\NSSLC.Server\NSSLC.Server.csproj
```

产物位于 `Build\bin\NSSLC.Server\Debug\net10.0\`（`Directory.Build.props` 统一改写输出根）。

### 3.2 启动

```powershell
dotnet Build\bin\NSSLC.Server\Debug\net10.0\NSSLC.Server.dll "src\World\科研.wld"
```

参数契约（`Program.cs`、`ServerWorldLoader.cs`）：

| 参数 | 说明 |
| --- | --- |
| 第一个非 `--` 参数 | 世界文件路径，按当前工作目录解析；省略时回退到环境变量 `NSSLC_WORLD_FILE`，再回退到 `AppContext.BaseDirectory` 上跳四级的 `src/World/科研.wld`；文件不存在直接抛 `FileNotFoundException` |
| 监听地址/端口 | 固定 `127.0.0.1:7777`，没有命令行开关；不要与旧 `MinimalImplementation.Server` 的 `--world/--listen-port` 混用 |

世界路径建议始终显式传入：默认路径依赖二进制所在目录布局，`dotnet run` 与直接运行
`Build\bin` 产物得到的基准目录不同。

### 3.3 就绪判定与日志判读

启动阶段固定序列（以 2026-11-20 22:11 实测为例）：

```text
INFO ecs.world.tile-entities chests=493 signs=0 tileEntities=0 pylons=0
INFO ecs.npc.spawned guide=world-spawn:4195,541 slime=world-spawn+3tiles:4198,541 ...
INFO ecs.protocol.world_cache_ready sections=672 compressedBytes=8402777 elapsedMs=6167
INFO ecs.server.ready ai=manual listen=127.0.0.1:7777 world=8400x2400 path="...\src\World\科研.wld" spawn=4195,541
```

- `ecs.protocol.world_cache_ready` 表示世界区段压缩缓存预热完成；`ecs.server.ready` 之后客户端才可连接。
- 会话建立序列：`ecs.session.player_bound` → `ecs.protocol.player_info slot=0` →
  `ecs.protocol.world_data` → `ecs.protocol.initial_spawn` → `ecs.protocol.active` →
  `ecs.npc.network_sync slot=0 type=22`、`slot=1 type=1`（向导与史莱姆）。
- 夹具客户端测完主动断开时会出现
  `WARN ecs.connection.failed type=SocketException detail="远程主机强迫关闭了一个现有的连接。"`
  以及紧跟的 `ecs.session.player_unbound`；这是正常的会话回收，不是服务器故障。

### 3.4 停止

前台 `Ctrl+C` 结束。服务器停止时不写回世界文件，调试期间的物块变更只存在内存。

## 4. HeadlessPacketProxy（抓包代理）

### 4.1 构建

```powershell
dotnet build Build\runtime\HeadlessPacketProxy\HeadlessPacketProxy.csproj
```

产物位于 `Build\bin\HeadlessPacketProxy\Debug\net10.0\`；`Build/runtime/HeadlessPacketProxy/bin/`
下的副本是历史构建残留，不作为入口。

### 4.2 启动

```powershell
dotnet Build\bin\HeadlessPacketProxy\Debug\net10.0\HeadlessPacketProxy.dll 7778 7777 Build\runtime\latest-client-packet-proxy.log
```

```text
usage: HeadlessPacketProxy <listenPort> <targetPort> <logPath>
```

参数个数不对或端口非整数时打印用法并以退出码 `2` 退出。日志目录会被自动创建，
`logPath` 每次运行覆盖写入。

### 4.3 行为与日志格式

- 只接受 **一个** 客户端连接：`AcceptTcpClientAsync` 一次，目标连上后打印 `CONNECTED`，
  中继结束即退出进程。下一次调试必须重启代理。
- 逐帧日志：`<UTC ISO8601> C2S|S2C id=<包ID> length=<帧长> hex=<整帧十六进制>`。
- 帧格式：前 2 字节为小端总长（含 2 字节头），第 3 字节为包 ID；`length` 必须落在
  `3..65535`，否则打印 `INVALID length=...`；读不满一帧打印 `TRUNCATED length=...`。
- 任一方向结束都会落一条 `CLOSED <异常类型>: <消息>`；客户端正常断开也可能带异常文本，
  以服务器端 `player_unbound` 判断会话是否已回收。

## 5. 最新客户端（`-networktest` 无 UI 场景）

### 5.1 启动

```powershell
& 'D:\TRbackup\最新的客户端\bin\Debug\net40\Terraria.exe' `
  -networktest npcprobe `
  -testresult Build\runtime\latest-client-npcprobe-result.json `
  -join 127.0.0.1 -port 7778 `
  -tile-frame-important Build\runtime\latest-client-frame-important.json `
  -testtimeoutms 60000
```

`-networktest` 在 `WindowsLaunch.Main` 最开始拦截，早于任何游戏状态与平台/UI 初始化；
场景内 `Main.instance`、`Main.graphics` 恒为空，`Program.SavePath` 被改写到结果目录下的
`ClientState`，不会污染玩家存档。

### 5.2 参数

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `-networktest <场景>` | 是 | 触发无 UI 模式并选择场景；未知场景抛 `Unknown network test scenario` |
| `-testresult <路径>` | 是 | 结果 JSON 路径；原子写入（先写 `.tmp` 再替换），目录不存在会自动创建 |
| `-testtimeoutms <毫秒>` | 否 | socket 读超时，默认 `60000`，必须为正整数 |
| `-join <地址>` | 否 | 服务器地址，默认 `127.0.0.1` |
| `-port <端口>` | 否 | 服务器端口，默认 `7777`；走抓包时改 `7778` |
| `-password <密码>` | 否 | 握手密码，写入 `Netplay.ServerPassword` |
| `-tile-frame-important <json>` | 否 | `{"frameImportant":[bool,...]}`，项数必须等于客户端 `Main.tileFrameImportant.Length`（754），整表覆盖客户端解码表；不传则用客户端内置表 |
| `-testautomation <场景>` | 内部 | 由夹具自动设置，不要手工传 |

### 5.3 场景清单

| 场景 | 行为 | 在 NSSLC 服务器上的可用性 |
| --- | --- | --- |
| `hello` | 仅握手，验证包 1→3 与槽位分配 | 有实测证据（`headless-hello-result.json`） |
| `npcprobe` | 世界元数据 + 初始区段 + 出生（包 49/12/129）+ 两个包 23，校验向导与史莱姆均为 `serverAuthoritative` 且可见 | **推荐主用**，2026-11-20 两次 PASS |
| `world-request` | 收包 7 并校验世界名称/ID/宽高 | 未在本服务器回归 |
| `world-player` | 在 `npcprobe` 基础上做 207 帧人物控制、600 tile 长距离移动、跨区段请求、物块破坏与区段刷新 | 无 UI 夹具限制，见第 8.1 节 |
| `admission`、`ping`、`gateway`、`password-rejected`、`default-deny` | 面向旧 `NSSLC.Tools.NetworkServer` 网关夹具的准入/模块/拒绝路径 | 未在 NSSLC ECS 服务器回归 |

### 5.4 控制台与结果判读

控制台按收发顺序打印 `TX <包ID> <帧长>`、`RX <包ID> <帧长>`，握手成功打印
`HANDSHAKE accepted slot=0`，最后一行 `PASS <场景>` 或 `FAIL <场景>`；失败时退出码为 `1`。

结果 JSON 固定字段：`scenario`、`success`、`message`、`elapsedMilliseconds`、`playerSlot`、
`netMode`；世界场景附加 `worldName/worldId/worldWidth/worldHeight/worldSectionsReceived`；
`world-player` 另有 `controlFramesSent/sawRightControl/sawJumpControl/movementDistancePixels/
movementSectionTransitions/requestedSections/destructionTargetX/Y/Type/tileBreakRequestSent/
tileUpdateReceived/tileSectionRefreshReceived`；`npcprobe` 附加 `npcSnapshot`，格式为：

```text
guide(active=True,type=22,authoritative=True,shimmer=0,x=67149.5,y=14008.0);slime(active=True,type=1,authoritative=True,shimmer=0,x=67368.0,y=8654.0)
```

判定标准：`success==true`、`playerSlot==0`、`worldSectionsReceived>0`；`npcprobe` 要求两者
`active=True`、`authoritative=True`、`shimmer=0`。

## 6. RawNpcMonitor（裸包 NPC 监视器）

### 6.1 构建与运行

```powershell
dotnet build Build\runtime\RawNpcMonitor\RawNpcMonitor.csproj
dotnet Build\bin\RawNpcMonitor\Debug\net10.0\RawNpcMonitor.dll
```

必须在仓库根目录运行：输出路径按当前工作目录拼成 `Build\runtime\raw-npc-monitor.jsonl`。
监视器硬编码 `127.0.0.1:7778`，因此前面必须有一个 `7778 → 7777` 的代理进程。

### 6.2 行为

1. 发送包 1（`Terraria326` 版本串），要求包 3；2. 发包 6，要求包 7；3. 发包 8（`FF`×9）直到收到包 49；
4. 发包 12；5. 观察 `5000 ms`：包 20 只计数，包 23 解析后写 JSONL，其他包写 `active id=<ID> length=<帧长>`；
6. 结束时写 `summary npcPackets=<N> tileUpdates=<M>` 并在控制台打印同一统计与输出路径。

### 6.3 输出字段

每行一个 JSON 对象：`Slot`、`Generation`、`X`、`Y`、`VelocityX`、`VelocityY`、`Target`、
`Flags1`、`Flags2`、`Ai`（按标志位出现的 4 个浮点）、`Type`、`Life`、
`ServerAuthoritative`（`Flags2 & 0x20`）、`Timestamp`（UTC）。

用途：核对包 23 的到达节奏（相邻 `Timestamp` 间隔）与 `ServerAuthoritative` 位；服务端权威
模式下客户端 `NPC.UpdateNPC` 不做本地 AI 与插值，画面严格等于最后一次快照，包 23 的节拍
就是抖动源。

## 7. 推荐流程

### 7.1 流程 A：npcprobe 冒烟（默认选择）

1. `dotnet build src\NSSLC.Server\NSSLC.Server.csproj`
2. 启动服务器，等待 `ecs.server.ready ai=manual|shared listen=127.0.0.1:7777`
3. 启动代理 `7778 7777 Build\runtime\latest-client-packet-proxy.log`
4. 运行客户端 `-networktest npcprobe -port 7778 -tile-frame-important Build\runtime\latest-client-frame-important.json`
5. 判定：控制台 `PASS npcprobe` + 结果 JSON `success:true` + `npcSnapshot` 两项 authoritative
6. 关闭代理（进程已自动退出）与服务器

2026-11-20 22:12 实测链路：代理 `READY/CONNECTED` → 客户端 `TX 1 15 / RX 3 5 / HANDSHAKE accepted slot=0`
→ `RX 7 173` → 15 个包 10 → `RX 49` → `TX 12` → `RX 129` → `RX 23 30`、`RX 23 41` → `PASS npcprobe`（2297 ms）。
证据：`Build/runtime/latest-client-npcprobe-current-result.json`、`.stdout.log`、
`latest-client-packet-proxy-current.log`、`slime-manual-server-current.stdout.log`。

### 7.2 流程 B：抓包时序分析（抖动/卡顿类问题）

1. 按流程 A 起服务器与代理，客户端照常跑 `npcprobe`
2. 在代理日志里筛 `S2C id=23`：相邻时间戳差即 NPC 快照到达间隔；`S2C id=20` 计数即 Tile 洪水强度
3. 与服务器 `stdout` 的 `ecs.npc.network_sync`、`ecs.protocol.*` 时间点交叉核对
4. 判读：包 23 节拍抖动且其间夹大量包 20，说明出站队列被 Tile 更新挤压，而不是客户端渲染问题

### 7.3 流程 C：RawNpcMonitor 裸包观察

1. 起服务器 → 起代理（`7778 7777`）
2. 运行监视器，等待 5 秒观察窗口结束，读 `Build/runtime/raw-npc-monitor.jsonl`
3. 监视器与客户端 **不能共用同一个代理实例**（代理单连接），两者要分两次会话、分别重启代理

## 8. 已知限制与故障排查

### 8.1 `world-player` 在无 UI 夹具中的已知限制

包 49 之后原版出生流程进入 `Player.Spawn` → `Main.BlackFadeCameraTeleport` →
`Lighting.Clear()`，夹具未初始化光照而抛 `NullReferenceException`（
`latest-client-world-player-fixed-result.json`，2026-11-20 21:55）。
这是客户端夹具的初始化边界，不是服务器故障；NPC/出生验证请用 `npcprobe`。

### 8.2 frame-important 表不匹配

症状：`System.IndexOutOfRangeException` 于 `Terraria.NetMessage.DecompressTileBlock_Inner`
（`latest-client-world-player-result.json`，2026-11-20 19:53）。
原因：客户端解码包 10/20 的表与服务器编码用的表不一致。
处理：始终带 `-tile-frame-important Build\runtime\latest-client-frame-important.json`（754 项，
与客户端 `Main.cs` 的 398 个唯一真值项一致）；更换客户端版本后必须重新导出并与服务器
`ServerWorldLoader.CreateLatestClientFrameImportance` 的强制项（435-439、647-652、693、694、706、753）
核对，`Build/runtime/compare_fi.py` 提供了两侧 `tileFrameImportant[...] = true` 清单的比对思路。

### 8.3 `npcprobe` 报 `unexpected active packet 20`

同步窗口内服务器发来了物块更新（液体流动、另一会话活动等），夹具在此阶段只接受包 9/10
（`latest-client-npcprobe-result.json`，2026-11-20 21:58）。
处理：确认没有其他会话/残留连接，重跑一次；持续出现再查服务器侧 Tile 变更来源。

### 8.4 代理相关

- 每个代理实例只服务一个连接；第二次运行客户端前必须重启代理，否则连接被立即关闭。
- 历史失败：`CLOSED InvalidOperationException: The stream is currently in use by a previous operation`
  （`raw-monitor-priority-proxy.log`），此时监视器日志只有 BOM 没有内容，重跑即可。
- 中继期间任一端异常断开，代理只记录 `CLOSED` 并退出，不会自动重连。

### 8.5 端口占用

```powershell
Get-NetTCPConnection -LocalPort 7777,7778 -State Listen -ErrorAction SilentlyContinue |
  Select-Object LocalPort,OwningProcess
```

有残留服务器时先结束进程再启动，否则服务器在 `ecs.server.ready` 之前即失败。

### 8.6 客户端重建现状

工作用 `Terraria.exe` 为 2026-10-31 产物，**当前源码重建不通过**：2026-11-20 的两次尝试
（`latest-client-build-net40.log`、`latest-client-headless-build-net48.log`）均以 193 个错误结束，
全部是 `Properties\AssemblyInfo.cs` 与 SDK 自动生成特性重复（CS0579）以及附属程序集区域性
（CS7059）。调整客户端源码前先解决该构建问题（可选方向：`-p:GenerateAssemblyInfo=false`
或从编译项排除重复的程序集特性文件，均未验证），否则以现有 exe 为准。

### 8.7 超时与世界预热

大世界首次启动的 `world_cache_ready` 约 6–8 秒（672 区段、8.4 MB）；`-testtimeoutms` 默认
60000 足够，若在慢磁盘上加大世界仍超时，先确认服务器已到 `ecs.server.ready` 再跑客户端。
