本文件规定仓库和项目层面的文件落位：根目录分层、生产代码与只读参考材料的边界、共享/服务端/
客户端项目边界、测试与文档的存放位置，以及目录移动、命名空间和迁移记录规则。

本文件不规定 ECS 领域内部的目录划分、组件与查询归属，不规定具体字段、组件 API、系统算法、
运行时框架或业务规则。领域内部组织继续遵循 [ECS 文件组织设计约束](ECS文件组织设计约束.md)，
组件命名和注册键遵循 [组件命名设计约束](组件命名设计约束.md)，依赖方向与职责归属遵循
[ECS 领域层与基础设施六边形架构边界](ECS领域与基础设施架构边界.md)。若某项变更同时涉及数据
模型或架构边界，必须另行记录设计决策。

## 2. 核心原则

### 2.1 交付边界优先

根目录和项目按交付边界组织，而不是按个人工作流或临时任务组织。维护者应能从路径判断一段
代码属于哪个交付物、由哪个项目编译、产物落在哪里。

### 2.2 路径只表达归属

目录路径表达归属，不表达 C# 命名空间、构建顺序或运行时执行顺序。命名空间、执行顺序和加载
顺序都不得由目录结构、文件名排序、目录枚举或项目文件顺序隐式决定。

### 2.3 按需建立目录与项目边界

没有真实文件、依赖或发布依据时，不新增目录，也不新建项目。项目边界只在出现独立的依赖、
测试、部署或发布需求时形成；不为模仿大型项目提前创建空的 `Shared`、`Server`、`Client` 目录。
该原则与 [ECS 文件组织设计约束](ECS文件组织设计约束.md) 第 2.3 节的领域内部按需引入原则同源。

## 3. 仓库级目录分层

根目录按交付边界组织，而不是按个人工作流或临时任务组织：

```text
/
  src/                 # 可复用库、共享领域、服务器、客户端和工具源码
  Test/                # 可执行验证项目与测试夹具
  dome/                # 独立工作区；其内部继续遵循本约束
  Context/架构设计/    # 已确认的架构与设计约束
  Context/约束/        # 编码、构建和流程约束
  Build/               # 构建脚本、生成物和缓存，不放业务源码
  .agent-workplace/    # Agent 私有过程产物，不作为业务源码入口
```

### 3.1 生产代码

- `src/` 存放正式生产源码，按项目边界和领域组织。
- `src/NSSLC.Infrastructure/分类参考/` 只存放供阅读、搜索和比对的参考材料，不是生产代码目录。禁止在其中新增、修改、移动或实现任何代码；正式生产项目也不得编译或引用该目录中的源码。需要实现基础设施能力时，应将实现放在正式的 `src/NSSLC.Infrastructure/` 生产目录，并由生产项目显式编译。
- 共享代码放在 `Share` 或等价的共享项目边界内；服务器、客户端和工具代码不得反向
  混入共享领域。
- `dome/` 是独立工作区时，使用 `dome/src/`、`dome/Test/` 和 `dome/dome1/docs/` 的内部边界；
  不把其源码平铺回根目录 `src/`。

### 3.2 测试与验证

- `Test/` 与生产项目平行，测试项目名称应能对应被验证的生产项目或领域。
- 测试按领域或验证目标组织，不建立全局无语义的测试杂物目录。
- 测试夹具、快照和记录数据放在对应测试项目内，生成性输出放入 `Build/` 约定目录。
- 一级目录按被验证的生产边界划分，验证类型与审计意图不进路径；目录、命名、放置和
  运行细则见 [Test 验证项目组织](../../Test/README.md)。

### 3.3 文档

- `Context/架构设计/` 只放已确认的架构、设计和约束文档。
- 临时草稿、审查过程和未归档记录放在 `.agent-workplace/` 或对应流程目录，不冒充正式
  约束。
- 正式约束应在 `AGENTS.md` 或其他项目入口中提供链接，避免只靠文件名发现。
- `docs/` 不维护全局索引文件，文档按领域目录直接定位；依据见
  [CR-2026-11-22 移除 docs 索引层](../../docs/cr/CR-2026-11-22-remove-docs-index.md)。

## 4. 项目边界与端别扩展

当同一领域出现共享、服务端和客户端实现时，保持领域名一致，在平行项目中表达端别：

```text
src/
  Shared/
    Movement/
  Server/
    Movement/
  Client/
    Movement/
```

只有真实存在独立代码、依赖或发布边界时才拆分端别项目；不得为模仿大型项目而提前
创建空的 `Shared/Server/Client` 目录。端别拆分不改变领域名称，也不允许服务端或客户端
专属状态回流到共享层。

端别拆分只决定项目边界，不决定职责归属：哪一方持有权威状态、哪一方只做适配，继续遵循
[ECS 领域层与基础设施六边形架构边界](ECS领域与基础设施架构边界.md)，领域内部的目录划分
继续遵循 [ECS 文件组织设计约束](ECS文件组织设计约束.md)。

## 5. 目录、命名空间与迁移

- 目录路径表达归属，不自动决定 C# 命名空间；命名空间变更必须作为独立 API/依赖变更
  评估。
- 目录移动应优先保持行为、公共 API 和命名空间不变，除非变更目标明确要求同步调整。
- 目录与命名空间不一致可以是既定事实，不能在移动目录时顺手"修正"：例如
  `src/NSSLC/World/ComponentSystem/TileEntity/` 的代码仍位于 `namespace Terraria.World`，
  `src/NSSLC/Share/ItemUse/` 仍位于 `Terraria.Player`。这类解耦不构成缺陷，见
  [Test 验证项目组织](../../Test/README.md) 的命名说明。
- 迁移按小批次进行：先记录源路径与目标路径，再移动文件，随后修复引用并执行受影响
  项目的验证。
- 不得依赖文件名排序、目录枚举或项目文件顺序表达运行时执行顺序。ECS 系统之间的执行
  顺序仍按 [ECS 文件组织设计约束](ECS文件组织设计约束.md) 第 5 节和系统调度文档显式声明。

## 6. 新增与迁移验收

每次新增、移动、拆分或合并项目、目录、文件或文档时，必须检查：

- [ ] 新增文件落在表达交付边界或能力的目录，而不是只有技术类别或个人工作流的目录。
- [ ] 没有为模板完整性预建空目录、空项目或空的 `Shared/Server/Client` 端别边界。
- [ ] 生产源码没有与只读参考材料、构建产物、临时草稿或 Agent 过程文件混放。
- [ ] 目录移动没有未经批准地改变命名空间、公共 API 或运行时行为。
- [ ] 目录结构、文件名排序和项目文件顺序没有被用来表达构建、加载或运行时执行顺序。
- [ ] 新增或移动的测试项目落在 `Test/` 对应边界目录，并符合
  [Test 验证项目组织](../../Test/README.md) 的目录与命名规则。
- [ ] 文件与目录命名仍符合 [ECS 文件组织设计约束](ECS文件组织设计约束.md) 第 2.5 节和
  [组件命名设计约束](组件命名设计约束.md)。
- [ ] 受影响项目按 [构建与验证约束](../约束/构建与验证约束.md) 完成验证；输出位于
  `Build/bin/`。
- [ ] 变更说明包含源路径、目标路径、依赖影响和回滚方式。
- [ ] 领域内部的组织项同时按 [ECS 文件组织设计约束](ECS文件组织设计约束.md) 第 6 节核对。

## 7. 适用优先级

发生冲突时，适用以下优先级：

1. 安全、数据完整性和架构边界；
2. 项目或目录级 `AGENTS.md` 的更具体约束；
3. 本文件的仓库级和项目级文件组织约束；
4. [ECS 文件组织设计约束](ECS文件组织设计约束.md) 等主题文件的领域内部组织约束；
5. 一般命名和格式偏好。

任何例外都必须在对应架构文档或变更记录中说明原因、范围和撤销条件。
