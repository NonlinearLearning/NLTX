# ECS 组件命名设计约束

## 1. 文档状态

| 项目 | 约束 |
| --- | --- |
| 适用范围 | 本仓库全部 ECS 组件、组件基类、组件字段、组件运行时注册键、原型和测试引用 |
| 规范性质 | 正式设计约束 |
| 强制入口 | 根目录 `AGENTS.md` |
| 参考来源 | Space Station 14 master 源码取样；参考副本为 `C:\Users\shan\Downloads\ECS\space-station-14-master` |
| 适用阶段 | 新增、移动、拆分、合并、继承调整、重命名和运行时注册变更时 |

本文件规定 ECS 组件及其相关标识符的命名方式，不规定组件的数据结构、系统算法、网络
同步实现、目录位置或业务规则。目录归属继续遵循
[`ECS文件组织设计约束.md`](ECS文件组织设计约束.md)。命名变更如果影响原型、网络状态、
序列化或公共 API，必须按接口和数据迁移处理，而不能当作纯文本重命名。

本文件从实际代码中提取稳定模式，再将其收敛为本仓库的新代码约束。参考源码中已经存在
的历史命名、文件名与类型名不一致、缩写不一致或拼写问题不会自动成为新代码模板；保留
现有名称时按第 11 节登记为兼容例外。

## 2. 证据边界与核心原则

### 2.1 参考实现的观测范围

本次取样覆盖参考副本的 `Content.Shared`、`Content.Server`、`Content.Client`、
`Content.IntegrationTests` 和 `Resources`。以 `*Component.cs` 统计，三个内容项目共有
2055 个文件，其中 1969 个文件包含 `[RegisterComponent]`，37 个文件声明抽象组件类型
（其中少数同时带注册属性）；绝大多数具体组件使用注册属性，抽象组件基类通常不注册。

参考副本中的 `RobustToolbox` 目录未提供可枚举的源码内容，因此本文件不把未读取的框架
内部实现当作证据。运行时注册键、原型键和组件类型之间的关系，依据内容侧实际用法确认：

- `Resources/Maps/box.yml` 使用 `MetaData`、`Transform`、`Physics` 等组件注册键。
- `Content.IntegrationTests/Tests/PrototypeSaveTest.cs` 通过
  `IComponentFactory.GetComponentName` 在类型与原型组件键之间转换。
- `Content.Shared/Construction/Steps/ComponentConstructionGraphStep.cs` 通过
  `GetComponentName(component.GetType())` 与配置中的组件名比较。
- `ComponentNameSerializer` 被用于需要从 YAML 或数据字段读取组件名的场景，说明组件名
  是可验证的运行时数据，而不只是 C# 代码中的显示文本。

### 2.2 核心原则

1. **名称表达稳定语义。** 组件名首先说明它表示的能力、状态、触发条件或呈现状态，不能
   只描述当前系统、当前调用者或某次实现方式。
2. **一个组件只有一个身份。** C# 类型名、同名文件名和运行时注册键必须能够稳定映射；
   原型、测试、查询和序列化引用不能各自发明同义名称。
3. **能力优先于实体类别。** 可被多个实体使用的能力使用能力名，例如
   `PowerConsumerComponent`、`WieldableComponent`；只有确实只属于某一领域时才把实体或设备
   名放在前面，例如 `VendingMachineComponent`、`ZombieComponent`。
4. **状态、行为和呈现分开命名。** 持续状态、事件触发器、触发效果和客户端视觉状态使用
   可区分的词形，避免仅凭系统代码才能判断组件用途。
5. **边界必须可读。** `Base`、`Shared`、`Visuals` 等前缀或后缀只能表示稳定的继承、
   跨端或呈现边界，不能作为目录名的装饰或个人偏好。
6. **现有公共身份优先保持稳定。** 重命名组件会影响原型、配置、网络状态、存档、测试和
   运行时查询；除非变更目标明确要求，不得仅为追求更漂亮的名称而修改已发布身份。

## 3. 命名层次与通用语法

组件命名至少包含以下层次。新增组件时必须分别确认，而不能只检查 C# 类名：

| 层次 | 推荐形式 | 约束 |
| --- | --- | --- |
| C# 类型 | `<语义名>Component` | PascalCase；必须以 `Component` 结尾；名称表达领域或能力 |
| 文件 | `<类型名>.cs` | 与核心公开组件类型同名；不得用职责、目录或系统名替代类型名 |
| 运行时注册键 | 框架注册的规范组件名 | 全局唯一、大小写稳定；由组件工厂或注册机制确认，不手写猜测映射 |
| 原型/YAML 键 | 运行时注册键 | 与注册表一致；不能把 C# 类型名、文件名和原型键混用为三个身份 |
| 代码查询标识 | 类型化工厂或 `CompName` | 优先由 `GetComponentName<T>`、`CompName.Get<T>` 等类型化 API 得到 |
| 组件基类 | `Base<族名>Component` 或 `Shared<领域名>Component` | 仅用于抽象复用或跨端契约；具体规则见第 7 节 |

推荐的普通组件语法如下：

```text
<领域或能力><可选语义修饰><Component>
```

例如：

```text
AnomalyComponent
ArtifactCrusherComponent
WiresPanelComponent
WieldableComponent
```

不要把所有组件机械地写成实体类型加 `Component`。如果组件表示“可被某类实体使用的
能力”，应优先以能力命名；如果它只表达某个领域对象的组成部分，才使用该对象名。

## 4. C# 类型与文件命名

### 4.1 类型后缀

- 所有可附加到实体的具体组件类型必须以 `Component` 结尾。
- 组件文件必须使用完整类型名，例如 `AnomalyComponent.cs` 中定义
  `AnomalyComponent`。
- 不得新增 `FooCompComponent`、`FooComponentComponent` 或把 `Component` 重复拼接到
  类型名中。参考源码中的 `ContainerCompComponent` 等名称属于历史兼容例外。
- 组件类型不得使用 `Manager`、`System`、`Helper`、`Utility`、`Utils`、`Data` 或
  `Info` 作为无语义收容词。若确实表示实体上的管理状态，必须在设计说明中解释为什么
  它是组件状态而不是系统、定义或服务。

### 4.2 PascalCase 与缩写

- 类型、文件和公开成员使用 PascalCase；缩写按照项目已有词汇表保持一致。
- 新增缩写必须是领域、协议或外部数据格式中的稳定术语；不能为了缩短文件名临时造词。
- 同一命名族内不得同时出现 `Apc`、`APC`、`apc` 三种新写法。已有公开类型的大小写
  不因本约束自动改名。
- `Comp`、`Cfg`、`Mgr`、`Info`、`Data` 等缩写不得出现在新组件类型名中；它们不能替代
  组件真正表达的能力。
- 外部协议强制使用全大写缩写时，可以保留全大写，但必须在命名词汇表或该组件的设计
  说明中固定其写法。参考代码中的 `XAT`、`XAE`、`NPC` 等属于此类需谨慎维护的已有词。

### 4.3 公开类型的数量与辅助声明

- 一个文件只放一个核心公开组件类型；事件、枚举或状态对象只有在与该组件紧密耦合且
  不会造成类型查找歧义时，才允许放在同一文件中。
- 组件类型若被源生成器、网络状态生成器或注册器处理，必须满足对应框架的修饰要求，
  例如需要 `partial` 时不得省略；这些语言修饰不写入类型名，也不能用后缀替代。
- 组件不要使用泛型作为运行时注册身份。需要泛型复用时，把泛型放在抽象系统、查询或
  非注册辅助类型上，具体可附加组件仍使用明确的非泛型类型名。

## 5. 语义命名模式

### 5.1 持续状态与能力

表示实体持续拥有的能力、关系或状态时，使用名词或稳定的形容性能力词：

```text
WieldableComponent
BuckleComponent
AnomalyComponent
XenoArtifactComponent
VendingMachineComponent
```

组件名应能回答“实体拥有什么状态或能力”，而不是“某个系统现在要调用什么方法”。
例如，系统可以读取 `WieldableComponent`，但不应因为当前系统叫
`WieldingSystem` 就创建 `WieldingSystemComponent`。

### 5.2 事件触发组件

触发器组件按照 `TriggerOn<事件或条件>Component` 命名：

```text
TriggerOnCollideComponent
TriggerOnMeleeHitComponent
TriggerOnUiOpenComponent
TriggerOnInsertedIntoContainerComponent
```

参考实现的 `Content.Shared/Trigger/Components/Triggers/` 中大量组件遵循这一模式。事件名
必须对应实际订阅的事件、交互或生命周期边界，不能使用含义过宽的 `TriggerOnEventComponent`。

如果组件表示“发生触发后执行的效果”，使用 `<效果>OnTriggerComponent`：

```text
DamageOnTriggerComponent
RejuvenateOnTriggerComponent
SpawnOnTriggerComponent
RemoveComponentsOnTriggerComponent
```

触发条件与触发效果不要共用一个模糊名称；二者是不同的组件族，通常也由不同的系统处理。

### 5.3 能力、要求与提供者

以下词尾只有在语义成立时使用：

| 词形 | 使用条件 | 示例 |
| --- | --- | --- |
| `Provider` | 提供某种资源、弹药、配方或服务 | `AmmoProviderComponent`、`RecipeProviderComponent` |
| `Consumer` | 消耗某种资源并且该消耗关系是组件状态 | `PowerConsumerComponent` |
| `Holder` | 持有可被其他系统读取的状态或容器 | `GasMixtureHolderComponent` |
| `Requires<X>` | 组件能力有明确的前置条件 | `GunRequiresWieldComponent`、`VocalizerRequiresPowerComponent` |
| `...able` | 表示是否具有某种可执行能力或资格 | `WieldableComponent`、`CuffableComponent` |
| `Marker` | 组件仅作为稳定的存在标记或空间/业务标记 | `DamageMarkerComponent` |
| `Visuals` | 组件只保存客户端呈现所需的派生状态 | `PortableScrubberVisualsComponent` |

不要仅因为字段中有一个列表就使用 `Data`，也不要仅因为系统需要缓存就使用 `Cache`。缓存
是否是组件应由状态所有权决定，名称仍需说明缓存内容，例如 `...ActiveNodes` 所属的
`XenoArtifactComponent`，而不是泛化的 `ArtifactDataComponent`。

### 5.4 状态、效果与标记

- `State` 用于实体确实存在离散状态或状态快照时，例如状态枚举、同步状态或明确的
  `...State` 数据对象；不得把所有运行时数据都命名为 `State`。
- `Status` 用于持续的状态效果、抗性或状态标记，例如 `WeatherStatusEffectComponent`。
- `Effect` 用于有明确施加、移除或持续作用语义的效果，不用于普通配置数据。
- `Marker` 用于主要由“是否存在”表达语义的组件；如果组件还拥有大量独立数据，应改用
  能力或状态名。
- `Visuals` 只表示呈现侧状态，不表示一般的“可视化系统”。系统应使用
  `...VisualizerSystem` 或其他系统名，组件使用 `...VisualsComponent`。

## 6. 领域、端别与共享命名

### 6.1 领域词与能力词

命名顺序通常从领域/对象到能力/状态，再到 `Component`：

```text
<领域><能力或状态>Component
```

例如 `CargoPalletComponent`、`PowerSensorComponent`、`PlantTraitKudzuComponent`。
跨领域复用的能力应去掉不必要的实体前缀；禁止为了当前第一个使用者而创建
`Player...Component`、`Npc...Component` 等专属名称，除非组件确实只属于该领域。

### 6.2 `Shared` 前缀

`Shared` 不是 `Content.Shared` 项目中所有组件的必备前缀。只有下列情况之一才使用：

1. 类型是服务端和客户端共同继承或共同理解的抽象契约；
2. 类型本身代表跨端共享的基类状态，并且存在明确的端别具体类型；
3. 现有公共 API 已经以 `Shared` 身份发布，重命名会造成不必要的兼容破坏。

参考实现中：

- `SharedShuttleConsoleComponent` 作为共享抽象组件，客户端有
  `ShuttleConsoleComponent` 具体类型。
- `SharedAmeControllerComponent` 与服务端 `AmeControllerComponent` 形成共享基类和
  服务端扩展。
- `AnomalyComponent`、`WiresPanelComponent` 等本身位于共享项目，但没有 `Shared` 前缀，
  说明项目边界和类型语义是两个不同维度。

因此禁止把所有共享项目组件机械重命名为 `Shared<名称>Component`，也禁止把
`Shared` 当作“这个组件可能以后会跨端”的预测性标签。

### 6.3 服务端、客户端与视觉组件

- 服务端或客户端具体组件不默认加 `Server`、`Client` 前缀；端别由项目、命名空间和
  真实运行时边界表达。
- 共享组件与端别派生组件表示同一领域对象时，保留稳定的领域词，不要在每一层重新发明
  同义名称。
- 客户端只为呈现服务的组件使用 `...VisualsComponent`；其状态来源和更新系统必须在
  设计中说明。
- `NetworkedComponent`、自动状态生成等属性描述同步机制，不通过 `Networked`、`Synced`
  等词强行加入类型名。只有当“同步状态”本身就是领域语义时，才允许把 `State` 纳入名称。

## 7. 抽象基类与组件族

### 7.1 `Base` 基类

`Base<族名>Component` 只用于有稳定共同字段、共同生命周期或共同查询边界的抽象组件族：

```text
BaseTriggerOnXComponent
  -> TriggerOnCollideComponent
  -> TriggerOnMeleeHitComponent

BaseAccentComponent
  -> MothAccentComponent

BaseForceGunComponent
  -> ForceGunComponent
  -> TetherGunComponent
```

约束如下：

- `Base` 类型必须是抽象类型，除非框架有明确的非抽象基础组件约定并记录例外。
- 抽象基类默认不使用 `[RegisterComponent]`，不直接出现在实体原型的组件列表中。
- 具体子类必须有自己的完整语义名和注册身份；不得让 `BaseFooComponent` 充当多个没有
  区别的具体组件。
- 子类名不得重复父类已经表达的无意义词。父类为 `BaseTriggerOnXComponent` 时，子类
  使用 `TriggerOnCollideComponent`，而不是 `BaseTriggerOnXCollideComponent`。
- 只有复用状态和访问边界时才建立基类；如果只是复用几行工具逻辑，应放到系统或普通辅助
  类型中，避免通过继承制造伪组件族。

### 7.2 `Shared` 基类与具体类型

跨端组件族优先采用“共享契约 + 端别具体实现”的模式：

```text
SharedShuttleConsoleComponent
  -> ShuttleConsoleComponent       # Client
  -> <服务端具体组件>               # Server，若确实需要
```

共享类型的命名不能泄露服务端私有行为；服务端具体组件也不能把服务端专属字段倒灌到
共享基类。若没有具体端别实现或跨端消费方，直接使用领域组件名，不要预建 `Shared` 基类。

### 7.3 组合优先

组件继承只表达稳定的“是一种组件族”关系，不表达实体分类树。多个独立能力使用多个组件
组合；不要通过 `PlayerComponent`、`MachineComponent`、`SpecializedMachineComponent`
等继承层次聚合无关状态。实体类别若只是查询条件，应由组件组合和查询表达。

## 8. 运行时注册键与外部标识

### 8.1 注册要求

- 具体、可附加、可被原型或运行时创建的组件必须使用项目框架要求的注册方式，通常为
  `[RegisterComponent]`。
- 抽象基类、仅供继承的共享契约和非组件辅助类型不得伪装成可附加组件进行注册。
- 注册键必须全局唯一，并且大小写、拼写和含义稳定。组件类名相同但命名空间不同不能
  依赖命名空间自动解决原型键冲突；冲突时必须增加领域区分词或显式设计注册名。
- 新增组件不得为“以后可能会用”预留多个别名或同义注册键。

### 8.2 原型和代码引用

组件注册键是数据契约的一部分。新增或修改组件时必须检查：

- 实体原型中的 `type` 或等价组件键；
- `GetComponentName<T>`、`GetComponentName(type)`、`CompName.Get<T>` 等类型到键的
  转换；
- `ComponentNameSerializer`、组件白名单、构造图、状态效果和其他配置中的组件名；
- 测试、工具和保存/加载代码中的字符串引用；
- 网络状态、回放、快照或跨端注册表中是否存在独立的组件表。

当代码可以从类型得到组件名时，优先使用类型化 API，不要手写字符串：

```csharp
// 推荐：类型是唯一来源，重命名检查点集中在工厂和迁移处。
var name = componentFactory.GetComponentName<MyComponent>();

// 仅在配置、原型或外部协议要求字符串时使用，并通过对应序列化器校验。
[DataField(customTypeSerializer: typeof(ComponentNameSerializer))]
public string RequiredComponentName = string.Empty;
```

如果框架默认将 C# 类型名的 `Component` 后缀转换为原型键，必须以框架实际注册结果为准；
不要在业务代码中自行实现“去掉后缀”或大小写转换规则。

### 8.3 重命名规则

组件重命名必须先回答以下问题：

1. 是只改 C# 类型名，还是同时改变文件名、注册键和原型键？
2. 现有地图、实体原型、构造图、白名单、状态效果、测试和工具是否仍能读取旧键？
3. 网络状态、回放、存档或外部包是否把组件键作为持久化数据？
4. 框架是否支持旧键别名或迁移？如果不支持，是否需要一次性数据迁移？
5. 查询、系统订阅和跨端具体组件是否需要同步改名？

迁移说明必须记录旧类型/旧键、新类型/新键、受影响项目、数据迁移方式、兼容窗口和回滚
方式。不得先改类名，再靠编译错误逐个猜测原型和运行时影响。

## 9. 组件字段与成员命名

组件名是第一优先级；但组件字段直接构成原型、网络状态和调试界面，所以也必须保持可读
且可推断。

### 9.1 一般规则

- 公共字段、公共属性和方法使用 PascalCase；私有字段使用 `_camelCase`，遵循仓库 C# 风格。
- 字段名描述数据，不以组件名重复开头。例如 `WiresPanelComponent.Open` 优于
  `WiresPanelComponent.WiresPanelOpen`。
- 集合使用复数或能表达集合语义的名词，例如 `Actions`、`CachedActiveNodes`、
  `NodeVertices`；单个引用使用单数。
- 数量使用 `Count`，索引使用 `Index`，上限/下限使用 `Max`/`Min`，不要用含糊的
  `Value` 承载多个业务含义。
- 字段不能用方法名伪装副作用。表示配置或缓存的字段使用名词；表示触发条件的组件名
  使用第 5.2 节的 `TriggerOn...` 或 `...OnTrigger` 语法。

### 9.2 布尔值

布尔字段应读起来像一个可判断的命题：

| 语义 | 推荐词头或词形 | 示例 |
| --- | --- | --- |
| 是否处于状态 | `Is...`、过去分词或直接状态词 | `IsDecayed`、`Suppressed`、`Open` |
| 是否拥有/存在 | `Has...` | `HasPower`、`HasFuelJar` |
| 是否允许能力 | `Can...`、`Allow...` | `CanShuttle` |
| 是否应执行 | `Should...`、`Auto...` | `AutoLock`、`Should...` |
| 开关启用 | `Enabled`、`Active` | `Enabled`、`Injecting` |

新字段不得使用 `Is`、`Has`、`Can` 混乱表达相反含义，也不得增加无语义的 `Bool` 后缀。
如果使用否定语义，例如 `IgnoreOtherNonHard`，必须确保调用处读起来不产生双重否定。

### 9.3 实体、原型、组件和时间标识

| 数据 | 推荐后缀或词形 | 说明 |
| --- | --- | --- |
| 实体引用 | `...Uid`、`...Entity`、`...Entities` | 根据项目对 `EntityUid` 和实体集合的既有约定命名 |
| 实体原型 | `...Prototype`、`...PrototypeId`、`EntProtoId` 对应语义名 | 不把实体原型 ID 与组件 ID 混称 |
| 组件注册键 | `...ComponentName`、`CompName` | 使用 `ComponentNameSerializer` 或类型化工厂 |
| 绝对时间点 | `...Time`、`...Moment`、`...At` | 例如 `NextPulseTime`、`DecayMoment` |
| 持续时长 | `...Duration`、`...Length` | 例如 `CrushDuration`、`MinPulseLength` |
| 延迟/冷却 | `...Delay`、`...Cooldown`、`...CooldownRemaining` | 明确是间隔、剩余时间还是结束时刻 |

不要用一个名为 `Id` 的字段同时表示实体 ID、原型 ID、组件注册键或数据库 ID。已有公共
字段名保持兼容，但新字段必须让 ID 的命名空间可推断。

### 9.4 组件字段与同步属性

`DataField`、`AutoNetworkedField`、`ViewVariables` 等属性描述字段的序列化、同步和调试
可见性，不通过字段名重复编码。例如不要因为字段被网络同步就命名为
`NetworkedCurrentState`；应该使用领域名 `CurrentState`，把同步属性放在声明上。

## 10. 禁止与推荐清单

### 10.1 禁止新增

- `ComponentComponent`、`CompComponent` 或其他重复后缀。
- 没有领域语义的 `DataComponent`、`InfoComponent`、`ManagerComponent`、
  `SystemComponent`、`HelperComponent`、`UtilsComponent`。
- 把所有 `Content.Shared` 组件统一加 `Shared` 前缀。
- 把所有客户端组件统一加 `Client` 前缀，或把所有服务端组件统一加 `Server` 前缀。
- 用 `VisualizerComponent` 表示普通视觉状态；新组件使用 `VisualsComponent`，
  `Visualizer` 保留给负责处理视觉状态的系统或明确的历史兼容 API。
- 使用未注册、未校验的自由字符串作为组件身份来源。
- 以文件名排序、系统名或当前第一个使用者决定组件名。
- 为解决命名冲突复制一个语义相同的组件，再让两个系统分别维护。
- 未记录迁移影响就改变已有组件的注册键、原型键或跨端公共类型。

### 10.2 推荐做法

- 先写出组件回答的问题：“实体拥有什么能力/状态，或在什么事件上触发什么效果？”
- 先找领域词汇表，再选择 `Provider`、`Holder`、`Requires`、`Marker`、`Visuals` 等
  受控词形。
- 查询优先以组件类型为入口，运行时字符串只在数据契约要求时出现。
- 对抽象族使用 `Base`，对跨端契约使用 `Shared`，对客户端派生状态使用 `Visuals`，
  不把这些词当作万能前缀。
- 新建组件前搜索同义组件、已有注册键和已有字段，优先扩展或组合已有组件。

## 11. 既有命名与兼容例外

参考源码中可以观察到以下历史情况；它们用于说明迁移风险，不是新代码模板：

| 现象 | 参考例子 | 处理方式 |
| --- | --- | --- |
| 文件名与核心类型名不一致 | `Content.Shared/Actions/Components/ActionContainerComponent.cs` 定义 `ActionsContainerComponent` | 新文件必须同名；旧文件只有在独立迁移中处理 |
| 文件名包含旧语义，类型已调整 | `Content.Shared/Botany/Components/ConsumeExudeGasGrowthComponent.cs` 定义 `PlantConsumeExudeGasComponent` | 不复制旧文件名模式；重命名必须检查原型和引用 |
| 文件名保留历史拼写，类型使用规范拼写 | `Content.Shared/Trigger/Components/Effects/RejuventateOnTriggerComponent.cs` 定义 `RejuvenateOnTriggerComponent` | 新文件必须避免拼写分叉；旧文件名只有在迁移中处理 |
| 视觉组件文件名使用 `Visualizer`，类型使用 `Visuals` | `Content.Client/Kudzu/KudzuVisualizerComponent.cs` 定义 `KudzuVisualsComponent` | 新组件统一使用 `...VisualsComponent`；旧路径作为兼容债务记录 |
| 类型含冗余 `Comp` | `Content.Shared/Containers/ContainerCompComponent.cs` | 不新增同类名称；若迁移需记录运行时键和原型影响 |
| 领域缩写和 PascalCase 混用 | `XAT`、`XAE`、`NPC` 与 `Apc` 等 | 维护既有公共名称；新族固定一种写法并登记词汇 |

本仓库遇到既有例外时，必须保留其公共 API 和运行时键，除非明确批准迁移。例外记录至少
包含：旧名、保留原因、影响范围、迁移触发条件、兼容截止条件和验证方式。不得以“参考项目
也有这个名字”为理由继续扩大例外。

## 12. 新增与迁移验收

每次新增、移动、拆分、合并、继承调整或重命名 ECS 组件时，必须检查：

- [ ] 组件名表达稳定的领域、能力、状态、触发条件或呈现状态。
- [ ] C# 类型为 PascalCase，并以一个且仅一个 `Component` 后缀结束。
- [ ] 核心公开组件类型与文件名完全一致。
- [ ] 没有新增 `Comp`、`Data`、`Info`、`Manager`、`System` 等无语义收容词。
- [ ] `Base` 仅用于抽象组件族，具体组件没有错误继承或注册基类名。
- [ ] `Shared` 只用于稳定的跨端契约或历史公共 API，没有机械添加。
- [ ] 客户端呈现状态使用 `VisualsComponent`，且与权威状态的来源边界明确。
- [ ] 事件触发器和触发效果分别使用 `TriggerOn...` 与 `...OnTrigger` 等可读词形。
- [ ] 组件注册键全局唯一，并已由实际注册表确认。
- [ ] 原型、YAML、构造图、白名单、状态效果和测试没有遗留旧键或错误字符串。
- [ ] 能通过类型化工厂取得组件名的代码没有重复手写字符串映射。
- [ ] 字段使用 PascalCase，布尔值、实体引用、原型 ID、组件名和时间字段的语义可推断。
- [ ] 缩写、大小写和领域词汇与同一命名族一致。
- [ ] 重命名说明记录旧名、新名、注册键、依赖影响、数据迁移和回滚方式。
- [ ] 受影响项目和验证程序按仓库构建约束完成验证；生成物仍位于 `Build/bin/` 等约定目录。

## 13. 适用优先级

发生冲突时，适用以下优先级：

1. 安全、数据完整性、网络/持久化兼容性和架构边界；
2. 项目或目录级 `AGENTS.md` 的更具体约束；
3. 本文件的组件命名和运行时标识约束；
4. `ECS文件组织设计约束.md` 的目录和文件组织约束；
5. 一般 C# 命名和格式偏好。

任何例外都必须在对应架构文档或变更记录中说明原因、范围、兼容影响和撤销条件。
